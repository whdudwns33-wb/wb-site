# CRM·CS·학원·센터 통합 고객 카드 v1

작성: 2026-10-27. 사용자 요청에 따른 기획·구현 기준. **코드·가상 검증과 운영 배포·실고객 연결은 별개**다.

## 1. 전체 구조와 원본 책임

세일즈데스크의 기존 고객 상세를 전체 보기의 시작점으로 삼는다. 기존 고객을 대표 카드로 선택하고 자녀·성인 대상을 명시적으로 등록해 앱별 원본 ID를 연결한다. 기존 리드가 아동별로 나뉘어 있어도 이름·전화·HubSpot 연락처만으로 리드를 병합하지 않는다.

| 앱 | 담당 원본 | 통합 카드의 표시 |
|---|---|---|
| CRM | 영업 단계·상담·후속 연락·등록/보류·관계 관리 | 기존 고객 정보·활동, 통합 카드 |
| 학원 총괄 | 총괄 학생·출결·청구·수납 | 지정한 학생의 요약 |
| 블렌디드·독해력 | 각 앱 학생·출결·등하원 | 지정한 학생의 요약 |
| 영어 | 학생·프론트 출결/등하원·청구 | 요약, 같은 프론트 출결/등하원 ID는 타임라인 중복 제거 |
| 사고력 | 학생·수업·등하원 | 지정한 학생의 요약 |
| 센터 포털 | 검사·해석·관계/혜택·전화·설치 확인 | 기존 허용 요약과 원본 진입 |
| 메인 CS | 티켓·처리 단계, 기관·담당·긴급도·기한 | 보호자 기준 CS 요약·해당 티켓 진입 |

검사 점수·결과지·상담 원문·비밀 메모를 통합 API에 넣지 않는다. 출결·수납·학생·고객 원본을 CRM으로 복사해 수정하지 않는다. 친구맺기·서포터즈·맘스쿨의 모집·후속 연락은 CRM, 실제 참여·혜택 원본은 기존 포털/관계 기록을 유지한다. 맘스쿨은 검사 후 보호자4~6명의 주제별 차 모임, 성향검사 월2만원은20만원 검사비 분납이다. 이번 변경으로 상품·동의·발송 정책을 바꾸지 않는다.

## 2. CRM 화면과 연결 절차

1. 기존 고객 상세 위에 **통합 고객 카드**를 둔다. 원장만 표시·조회·연결하며 직원·파트너에게 새 원장 데이터 권한을 주지 않는다.
2. `가족 대상 추가`: 구분용 이름과 자녀/성인을 명시한다. 카드당 최대8명. 기존 리드·HubSpot 연락처·원본 학생은 수정하지 않는다.
3. 대상 → 원본 앱 → 원본 학생/센터 고객 ID → `원본 먼저 조회` 순이다. 학원 이름/학년을 확인하고 센터는 원본 페이지에서 신원을 직접 확인한다.
4. 연결 전·후 대상/기관/원본 ID를 표시하고 확인 체크 뒤 저장한다. 학원 신원 정보가 조회 뒤 바뀌었거나 연결 판본이 다르면 중단한다. 원장 확인을 이름·전화 자동 매칭으로 대신하지 않는다.
5. 자녀별 학생 상태·출결·등하원·수업·청구/수납을 펼쳐 보고 원본으로 이동한다. 총괄/하위 인원과 금액을 합산하지 않는다.
6. 통합 이력은 CRM 활동·조회한 학원 기록·CS 접수를 시간순으로 모은다. 날짜만 있으면 시각을 만들지 않고 업무일/생성/수정 시각을 구분한다.
7. 읽기 연결 해제는 원본·이력을 삭제하지 않는다. 같은 가정의 다른 자녀로 수정하려면 해제→원본 재확인→연결한다. 다른 고객 카드로 자동 이전하지 않는다.

**각 앱에서 돌아오기:** 학원5개 기존 원장 허브의 선택 학생과 포털 고객 상세/CS 전화 화면에 통합 카드 진입을 둔다. 주소는 `#/source/기관ID/원본ID` fragment다. 이름·전화·검사 정보를 넣지 않고 fragment는 서버 HTTP 쿼리로 전송되지 않는다. `noopener noreferrer`로 새 창을 연다. 로그인 뒤 활성·확인 연결만 역조회하며, 미연결이면 안내만 하고 고객을 만들지 않는다.

## 3. CS를 처리 업무 중심으로 재설계

접수 → 분류/위험 판단 → 기관·담당·긴급도·기한 확인 → 처리 중 → 고객 확인 대기 → 해결/종료 순이다. 기존 HubSpot 티켓 단계와 답변 승인·발송 보호를 유지한다.

| 구분 | 규칙 |
|---|---|
| 대상 | 보호자 연락처·자녀 이름/학년은 기존 계약. 원본 학생 ID와 CRM 고객 ID는 담당자가 확인 후 설정 |
| 기관 | 총괄·블렌디드·사고력·영어·독해력·센터. 기존 건은 미지정 보존 |
| 담당 | 관리자만 활성 CS 계정에 배정. 배정은 새 조회 권한 부여가 아님 |
| 긴급도 | 긴급/높음/보통/낮음. 위기·불만·환불 플래그는 긴급 하향 금지 |
| 기한 | 별도 CS 작업 기한. 원본 예약·청구일/HubSpot 기한을 몰래 바꾸지 않음 |
| 목록 | 모든 업무·내 담당·미배정·긴급·기한 지남과 기관·단계·분류·검색 조합 |
| 저장 | 관리자, 최초 updatedAt, 활성 담당자, 유효 날짜, 변경된 원본 ID 확인. 동시 수정이면 재조회 |
| 보호 | 위기는 기존 일반 초안·발송 중단. 불만/환불/결과 안내 승인 보호 유지. 자동 발송·딜 생성 없음 |

상태는 기존 HubSpot 티켓이 원본이다. 기관·배정·긴급도·작업 기한·확인한 참조만 앱 메타에 둔다. 이 참조는 **사람이 확인한 운영 메타**이며 자동 검증된 전사 공통 ID라고 주장하지 않는다. 영업 상담이 필요하면 담당자가 CRM으로 수동 인계한다.

## 4. 저장·ID·소유권

| 자료 | 저장 위치 | 제약 |
|---|---|---|
| 대표 고객 | 기존 leads 문서 | 기존 ID/판본/HubSpot 연결 유지 |
| 가족 대상 | `crm_customer_members` | 대상 ID, lead ID, 구분용 이름/유형·기록자·시각 |
| 읽기 연결 | `crm_customer_sources` | 기관+원본 ID 유일, 대상·활성·판본·확인자. 카드 최대48개 |
| 기존 포털 소유 연결 | `crm_portal_links` | 기존 HubSpot 쓰기 소유권·큐 보류 규칙 유지 |
| CS 메타 | `cs_ticket_meta` 추가 열 | 티켓 ID 기준 기관·담당·긴급도·기한·원본 ID·CRM ID |

읽기 연결로 원본/HubSpot 쓰기 소유권을 이관하지 않는다. 기존 ID를 새 ID로 덮지 않는다. 반복된 가족 추가 요청 ID는 같은 결과를 반환하고 내용이 다르면 거절한다. 연결은 판본을 대조하고 결과가 불확실하면 재조회하며 자동 재실행하지 않는다. CRM 전체 백업에는 새 대상/연결을 포함하고 키는 제외한다.

## 5. API·조회 범위·오류

| 주소 | 접근/기능 |
|---|---|
| `GET /api/customer-card?leadId=` | 기존 CRM 원장 인증, 대상/연결/원본/CS 요약 |
| `POST /api/customer-card/member` | 원장, 명시 대상 추가·요청 ID 중복 방지 |
| `GET /api/customer-card/source` | 원장, 고정 앱의 지정 ID 미리 보기 |
| `POST /api/customer-card/link` | 원장, 확인한 읽기 연결 활성/해제·판본 대조 |
| `GET /api/customer-card/resolve` | 원장, 기관+원본 ID 활성 연결 역조회 |
| 학원 기존 `/v1/apps/{appId}/records` | 전용 서버 읽기 키. 기존5개 API 재사용 |
| 포털 기존 `/api/integrations/salesdesk/families/{id}` | 기존 전용 키, 기존 허용 요약 재사용 |
| CS `GET /api/customer-card?contactId=` | 전용 서버 읽기 키. 같은 보호자의 앱 등록 티켓, 원본 연결 재검증 |

호출은 고정 HTTPS 주소만 사용한다. 사용자 URL·헤더·브라우저 쿠키 전달/리다이렉트를 금지하며 응답 크기·형식·앱/학생 ID를 검사한다. 일부 업무 조회 실패를0건으로 바꾸지 않는다. `connected/unlinked/not_configured/unavailable/disconnected`, 확인 시각과 이전 조회 여부를 구분한다. 고객 정보를 기기 저장소에 저장하지 않고 로그아웃 후 늦은 응답을 버린다.

**정확한 범위:** 학원은 원본별 최대20건의 기존 API **ID순 묶음**이며 전체/최근20건 보장은 아니다. total/more와 전체 원본 진입을 둔다. CS는 앱 메타에 등록된 티켓 최대20건으로 HubSpot 직접 생성 티켓 전부를 뜻하지 않으며 보호자 단위다. 센터 API는 관계·혜택·후속 건수·브런치 등 기존 요약이며 검사/해석의 구체 일시와 결과는 원본에서 확인한다. 통합 이력은 읽어 온 묶음의 최대100건이다. CS 목록의 업무/기관 필터는 기존 최근100건 안의 구분이며 전체 통계가 아니다.

## 6. 권한과 직원 연결의 경계

현재 구현은 원장 카드와 기존 승인된 CS 계정의 처리 흐름이다. 기관 필터/담당 배정을 접근 제어로 오해해 교사 계정을 일괄 개방하지 않는다.

목표 권한은 원장=허용 기관 전체, 관리자/데스크=소속 기관, 교사=원본 앱에서 허용된 담당 학생이다. 교사의 앱 내 접수/처리는 **원본 서버의 현재 세션·담당 학생 검증 → 기관에 묶인 서버 인증 → 중앙 CS API**가 필요하다. 원장 키/공용 CRM 토큰을 브라우저나 직원에게 배포하지 않는다. 이 직원별 매핑과 앱 내 입력 API는 후속이며 이번 메뉴로 완성됐다고 보고하지 않는다. 기존 MCP 실제 고객 수정의 조회→변경안→새 승인→저장→재조회 절차와 쓰기 권한은 유지한다.

## 7. 배포·수락 기준

1. CS/core 담당이 추가 스키마·설정을 검토하고 CS PR #72와 CRM PR의 CI를 통과한다. 운영 코드·DB를 백업한다.
2. CS만 배포하고 서버 `WB_CS_CUSTOMER_READ_TOKEN`과 CRM 저장소 시크릿 `WB_CS_READ_KEY`를 같은 전용 값으로 연결한다. 운영 HubSpot mock 상태는 요약 성공을 반환하지 않는다.
3. 학원은 기존 발급기로 `salesdesk-customer-card` 전용 읽기 클라이언트/허용 앱5개를 등록하고 `WB_ACADEMY_READ_KEY`로 공급한다. 기존 원장/MCP 키를 복사하지 않는다. 포털 키는 기존 것을 유지한다.
4. CRM은 기존 PR→checks→스쿼시 절차, Worker 추가 마이그레이션/코드→PC 화면 릴리스 순서다. 기존 클라우드 데이터·예약 동기화를 유지한다.
5. 학원 메뉴는 블렌디드 불변 릴리스를 보존하는 기존 설치 절차, 영어는 재빌드다. 포털은 실제 운영 브랜치/해시 런처를 확인해 템플릿 변경만 적용한다. 재부팅하지 않는다.
6. 격리 가상 고객으로 대상 추가→원본6개 조회→확인 연결→CS 배정/기한→역방향 진입→해제/충돌/재조회 검증한다. 운영 고객 일괄 연결·발송·결제·자동 딜 생성으로 시험하지 않는다.

계획·구현·합성 검사·브라우저 확인·PR/CI·운영 배포·실고객 연결을 각각 보고한다. 운영 키·CS 담당 검토·직원 매핑·실기기 확인이 남으면 통합 운영 완료라고 하지 않는다.
