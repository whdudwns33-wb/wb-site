# 원내 PC 를 서버로 — Cloudflare Tunnel 외부 공개

원장 요청: "클라우드플레어로 외부에서 접속하고 이 컴퓨터를 서버로."
**결정: A — 터널은 원장·강사 전용. 학생은 계속 운영 워커를 쓴다** (2026-10-11 원장 승인).
**덧붙여 같은 날 A.5 「금고」가 채택됐다 — 라이선스 자료(국어 팩)만 원장 PC 2대로 뺀다(§1.5).**
A 와 A.5 는 함께 선다: 학생은 계속 워커 주소를 쓰고, 워커가 자료만 PC 에서 받아 전달한다.
cloudflared 절차는 같은 날 Cloudflare 공식 문서에서 확인한 것이다.

**실행 키트(2026-10-12): [`reading-server/tunnel/`](../reading-server/tunnel/README.md)** — A 안을 원장 PC(Windows)에서
그대로 따라 하는 순서·설치 도구·점검 도구. 같은 날 공식 문서를 다시 확인해 §3·§4·§5 를 고쳤다
(원격 관리 터널이 권장 · Access 를 경로보다 먼저 · 호스트 전체(Path 비움) · 무료 50명 확인).
금고(A.5) 코드는 키트에 없다 — 아래 「남은 것」 원장 확인 4건이 먼저다.

## 0. 결론 셋

1. **도메인 하나가 선행 조건이다.** 도메인 없이 쓰는 퀵 터널은 **재시작마다 주소가 바뀌어**
   태블릿에 설치된 PWA·저장된 주소가 전부 끊긴다(§3). 금고(§1.5)에서는 더 직접적이다 — 주소가
   바뀌면 워커에 적어 둔 금고 주소가 매번 어긋나 자료가 안 나간다.
   → **원장 확인: 도메인은 이미 있다(2026-10-11).** 워커에 붙일 필요는 없다 — `wrangler.toml` 에
   `routes`·`custom_domain` 이 없고 `*.workers.dev` 만 쓰는 것은 그대로 두면 되고, 도메인은
   **터널 호스트 이름**에만 쓴다. (이 문서가 처음 "등록된 도메인이 없다"고 적은 것은 `wrangler.toml`
   에서 *워커* 설정을 보고 추정한 것이었다 — 도메인 보유 여부가 아니다.)
2. **데이터가 둘로 갈린다.** 운영 워커는 KV, 이 PC 서버는 `<DATA_DIR>/db.json` 이다. 옮기는
   코드가 없다 — `/api/admin/export` 는 양쪽에 있지만 **import 엔드포인트가 없다**(§1).
   금고(§1.5)는 이 문제를 피해 간다 — **라이선스 자료만** 옮기고 학생 기록은 KV 에 그대로 두므로
   옮길 기록이 없다. 그리고 국어 자료를 아직 채우지 않은 **지금이 옮길 것이 가장 적은 시점**이다.
3. **보안 헤더는 고쳤다.** 이 서버는 noindex·CSP·X-Frame-Options 를 아무것도 안 붙이고 있었다.
   localhost 전용이라 티가 안 났을 뿐이고, 터널을 붙이면 그대로 공개된다(§2).

## 1. 먼저 정해야 할 것 — 데이터를 어느 쪽에 둘 것인가

| | 운영 워커 `wb-reading` | 이 PC (Node 서버) |
|---|---|---|
| 저장소 | Cloudflare KV | `<DATA_DIR>/db.json` 파일 하나 |
| 학생 기록·시험 범위·팩 | 여기 있다 (지금 쓰는 것) | 빈 상태로 시작한다 |
| 켜고 끔 | 항상 켜짐 | PC 가 꺼지면 앱이 안 열린다 |
| 라이선스 자료 | KV | 원내 디스크 (밖으로 안 나간다) |

**지금 학생 기록은 KV 에 있다.** 터널만 붙이고 학생들이 새 주소를 쓰면 그 기록이 안 보인다.
일부는 워커 주소, 일부는 터널 주소를 쓰면 **기록이 두 갈래로 쌓인다** — 되돌리기 어렵다.

### 결정 — A (확정)

**운영은 워커에 그대로 두고, 터널은 원장·강사 전용으로만 쓴다**(관리 웹·팩 제작 검수).
학생은 계속 워커 주소를 쓴다. 데이터가 갈라지지 않고, 자료 수집·팩 제작을 PC 에서 하는
지금 흐름과 맞는다.

접지 않고 남겨 둔 갈래(나중에 다시 볼 때를 위해):

- **B. 전부 PC 로 이관.** 워커 `/api/admin/export` → `db.json` 인데 **import 경로가 없다.**
  먼저 만들어야 하고(반일 규모), 이관 중 학생 기록이 멈춘다. PC·인터넷이 끊기면 학생 앱
  전체가 멈춘다는 점도 같이 받는다.
- **C. 둘 다 운영.** 같은 학생이 양쪽에 다른 진도를 갖게 된다. 권하지 않는다.
- **A.5 「금고」 — 라이선스 자료만 PC, 학생 기록은 KV.** **채택됐다(2026-10-11 원장 결정).**
  A 와 B 사이다. 자세한 것은 바로 아래 §1.5.

### 1.5 채택 — A.5 「금고」 (2026-10-11 원장 결정)

학생 기록은 KV 에 그대로 두고 **라이선스 자료만** 원장 PC 로 뺀다. 학생은 계속 워커 주소를 쓰고
워커가 PC 를 대신 호출한다(오리진 하나 — CORS·토큰이 안 갈라진다). 접합부는 `worker.mjs` 의
`naesinKoStore(env)` **한 군데**다(`worker.mjs:255` 정의 · `:799` 호출, 다른 호출자 없음 — 2026-10-12 기준 행 번호).

#### 원장이 정한 것

| | 결정 |
|---|---|
| 라이선스 자료 | **원장 PC** (금고) |
| 학생 기록 | **KV 그대로** |
| 학생 기기에 팩 사본 | **두지 않는다** — 금고 둘 다 꺼져 있으면 그 단원은 아무도 못 연다 |
| 금고 대수 | **2대** (집 + 학원) |
| 백업 | **NAS** — 클라우드 동기화 폴더는 쓰지 않는다(KV 에서 뺀 자료를 두 번째 제3자 클라우드에 상시 복제하는 일이 된다) |
| 도메인 | **이미 있다**. 워커에 붙일 필요는 없다 — `wrangler.toml` 은 `*.workers.dev` 그대로 두고, 도메인은 **터널 호스트 이름**에만 쓴다 |
| 자료 수집 | 크롬 확장으로 족보닷컴 등에서. 2026-09-03 회신은 "학원 내부 무료 사용"을 다뤘고 **모으는 방식까지 물은 것은 아니다** — 원장 판단으로 진행(2026-10-11) |

#### 금고가 주는 것과 주지 않는 것 — 먼저 읽는다

금고는 자료가 **쉬고 있는 곳(at rest)** 을 우리 PC 로 옮긴다. **전송 경로에서 Cloudflare 를 빼지는
못한다** — 학생이 열 때마다 팩은 워커를 지나간다(워커가 금고에서 받아 학생에게 전달한다).
"Cloudflare 가 우리 자료를 아예 만지지 않는다"가 목표라면 금고는 그것을 주지 못하고, 그때는 B
(전부 PC 로 이관)뿐이다. **이 구분을 원장에게 확인받지 못했다** — 착수 전에 한 줄로 확정한다.

#### 어느 칸이 금고로 가는가 — 원장 결정 대기

확정: **라이선스 6칸** — `getPack`/`putPack` · `getPackIds`/`putPackIds` · `getPending`/`putPending`.

미정: **오버레이 2칸**(`getOverlay`/`putOverlay`). 오버레이는 "정본의 특정 항목을 학교 해석으로
덮어쓰는" 자리로, `answers[]` 에 **문항의 정답 문자열**이 들어간다(강사가 손으로 적는다,
`naesin-ko-api.mjs:410-424`). 정답 문자열을 라이선스 자료로 볼 것인가가 갈림길이다.

- **(ㄱ) 정답도 라이선스 자료다** → 금고는 **8칸**. 금고가 꺼질 때 막히는 범위가 넓어진다
  (학교 강조점까지 못 받는다). 설계 심사는 실무적으로 이쪽이 맞다고 봤다.
- **(ㄴ) 정답은 좌표일 뿐이다** → 6칸 그대로. 단 그 판단을 발문에도 일관되게 적용해야 하는데,
  **발문은 지면의 문장이라 좌표가 아니다** — 그래서 발문은 이미 기록에서 뺐다(아래).

분류를 손대지 않고 착수하면, 나중에 계약이 "원내 디스크에만"을 요구할 때 오버레이 때문에 처음부터
다시 해야 한다. **고르지 않은 쪽을 '왜 아닌가'로 이 문서에 남긴다.**

#### 착수 전에 정해 둔 네 줄

설계 심사(2026-10-11, 유출·가용성·경계 세 렌즈)가 세 갈래 모두 `fix-design-first` 를 냈고 blocker 가
10건이었다. 그 처방을 설계로 확정한 것이 아래 넷이다. **이 넷이 문서에 없는 상태로 코드를 쓰지 않는다.**

**① Access 를 어떻게 통과하는가** — §5 가 권고한 호스트 전체 Access 는 **사람 브라우저만** 통과시킨다.
워커의 `fetch` 는 팩 대신 로그인 HTML 을 받는다(저장소 전체에 서비스 토큰 언급이 0건이었다).
그래서 금고는 **관리 웹과 다른 호스트명**(`ko-vault-a.내도메인` · `ko-vault-b.내도메인`)에 두고,
그 호스트에는 사람 정책을 하나도 걸지 않고 Access **Service Auth** 만 건다
(`CF-Access-Client-Id` / `CF-Access-Client-Secret`). 그러면 `wb.내도메인` 의 호스트 전체 Access 가
손상되지 않고 §5 가 그대로 산다. 대안은 cloudflared `originRequest` 의 mTLS.
→ *확인됨(2026-10-12): self-hosted 응용 하나에 도메인 50개까지 담을 수 있다(공식 문서 'Multi-domain applications',
account-limits). 그래도 금고 호스트는 **Service Auth 전용 응용을 따로** 둔다 — 사람 정책과 한 응용에 섞으면
정책 하나를 고칠 때 다른 쪽이 같이 바뀐다. 또 2026-10-05 이후 만든 Zero Trust 조직은 **엄격한 서비스 토큰
인증이 항상 켜져** 있어(끌 수 없다) 토큰 헤더가 틀린 요청은 302 가 아니라 401/403 을 받는다 — 금고 클라이언트의
오류 분기는 이것을 전제로 짠다.*

**② 금고가 안 될 때 학생에게 뭐라고 보이는가** — `store.getPack` 의 계약이 *레코드 아니면 null* 이라
통신 실패가 `null` → **404** 가 되고, 404 는 학생 화면에서 *"선생님이 이 단원 자료를 아직 올리지
않으셨어요"* + **재시도 0회**다(`naesin-ko/index.html` `packFail`). 금고 장애가 선생님 탓으로 둔갑하고
영구히 안 올라온다. 그래서 금고 클라이언트는 **던지지 않고** 센티넬을 단 예외를 쓰고
(`e.wbStatus=503` · `e.wbSafeMessage`), `worker.mjs` 의 단일 catch 가 그것을 **먼저** 걸러
`json(503, { error: e.wbSafeMessage })` 만 낸다 — 원본 `message`·주소·본문은 버린다.
지금 그 catch 는 `detail: String(e && e.message || e)` 를 그대로 싣고(`worker.mjs:1151`), 금고가 JSON 이 아닌
본문(프록시 오류 HTML·잘린 팩)을 주면 **파싱 오류 메시지가 지문 조각을 품는다**. `res.json()` 은
try/catch 로 감싸 `reason:'parse'` 만 남긴다. 503 이면 학생은 30초·2분·10분·30분 재시도를 받는다.

**③ 쓰기는 몇 대에 성공해야 하는가 — "둘 다"는 모순이다** — 2대를 고른 근거는 "집·학원이 상보적이라
**둘 다 꺼진 창이 좁다**"인데 그것은 *읽기* 논거다. 쓰기에 "둘 다"를 요구하면 **둘 다 켜진 창**이
필요하고, 상보적일수록 업로드가 성립하지 않는다 — 지금 하려는 자료 채우기가 바로 막힌다.
그래서 **쓰기는 1대 + 지연 복제**로 간다: (a) 켜져 있는 금고 한 대에 버전으로 커밋하면 성공,
(b) 각 금고가 부팅할 때·주기적으로 상대에게서 자기보다 새 버전을 **당겨 온다**(pull 복제),
(c) 읽기는 두 금고의 버전을 비교해 **더 새 것**을 채택한다("먼저 응답한 쪽"이 아니다 — 그러면
1번 금고가 옛 자료를 조용히 200 으로 낸다). 한 대만 켜져 있을 때 업로드를 **거부하지 않고**
*"금고 A 에만 저장됐습니다 — B 를 켜면 자동으로 맞춥니다"* 로 받는다.
→ *원장에게 확인할 것: 두 PC 를 동시에 켜 둘 수 있는 시간대가 실제로 있는가. 없으면 (a)(b)(c)는
선택이 아니라 전제다.*

**④ 올리다 반만 들어가면 어떻게 되돌리는가** — 워커가 이전 값을 들고 있지 않아 첫 금고를 롤백할 수
없다. 그래서 금고 저장을 **버전 디렉터리 + `current` 포인터 2단 커밋**으로 둔다:
`pack/<id>/<ts>.json` 을 먼저 올리고(멱등·여러 번 써도 같다·롤백 가능), 마지막에
`{pack:<ts>, packIds:[…], pending:<ts>}` 를 가리키는 **수백 바이트짜리 커밋**만 보낸다. 그러면
① 정족수가 4MB 가 아니라 포인터에 걸려 어긋나는 창이 수십 밀리초로 줄고 ② 한쪽 커밋만 성공했을 때
직전 `ts` 로 되돌릴 수 있고 ③ `/admin/rubric` 의 세 쓰기(`putPack`·`putPackIds`·`putPending`)가
**한 커밋으로 묶여** 중간 상태가 사라진다. 지금도 `putPack` 성공 + `putPackIds` 실패 틈이 있고,
금고 2대는 그 틈을 2배로 만든다.
낙관적 잠금(`missingIds`)도 금고 쪽 **compare-and-set** 으로 내린다 — 워커가
`{ ifUpdatedAt: <읽은 값>, pack }` 을 보내고 각 금고가 자기 값과 다르면 **409** 로 거절한다.
쓰기 전에 두 금고 버전을 먼저 물어 **같지 않으면 아예 쓰지 않는다**.

#### 경계와 시크릿

- **금고 서버는 `127.0.0.1` 에 못 박는다.** 유일한 클라이언트는 같은 PC 의 `cloudflared` 다.
  `server.mjs` 모양을 그대로 베끼면 `0.0.0.0` 에 묶여 LAN 에 열린다(주소 없이 `server.listen(PORT)` 하던 자리).
  관리 서버 쪽은 2026-10-12 에 `HOST` 를 받게 고쳤다(`reading-server/host-bind.test.mjs`) — 금고도 같은 방식으로 묶는다.
- **금고 자체에 IP 별 실패 카운터 + 하드 잠금.** 속도 제한 코드가 이 저장소에는 워커에만 있다.
  터널을 우회해 닿은 요청 앞에는 아무것도 서 있지 않으므로, 이것이 없으면 비밀의 길이만이 방어다.
  비밀 비교는 `admin-auth.mjs:12-18` 의 `safeEqual` 을 그대로 쓴다(저장소가 이미 `===` 를 거부했다).
- **읽기·쓰기 비밀을 쪼갠다** — `KO_VAULT_READ_SECRET` / `KO_VAULT_WRITE_SECRET`. 하나로 묶으면
  비밀 유출의 결과가 '열람'이 아니라 **'팩 교체·목록 삭제'** 이고, KV 폴백이 없으니 금고가 1차
  사본이라 되돌릴 데가 없다. 금고는 읽기 비밀로 들어온 `POST`/`PUT` 을 거절하고, 워커는 **store
  메서드 종류로** 자격증명을 고른다(요청이 고르지 않는다 — `crm/portal-api.mjs:70` 과 같은 원칙).
- **시크릿 목록** — 주소 2개(한 값에 쉼표로) · Access 서비스 ID · Access 서비스 Secret ·
  읽기 비밀 · 쓰기 비밀 = **5개**. Access 응용을 호스트마다 따로 두면 7개가 된다. 금고는 둘 다 원장
  PC 로 신뢰 영역이 같아 하나로 둔다 — 대신 **서비스 토큰 하나가 두 금고를 다 연다**는 것을 받는다.
  `admin-secrets.yml` 에 `ko_vault` 선택을 하나 더한다(값은 `secrets.*` 에서 읽어 `::add-mask::`
  뒤 `wrangler secret put` — workflow_dispatch 입력으로 받지 않는다, 그 입력은 실행 기록에 남고
  이 저장소는 public 이다).
- **비밀 교체 절차를 지금 적는다** — 금고가 구·신 비밀을 **함께 받는 2단계**가 없으면 교체 한 번이
  국어 앱 전면 중단이다.
- **금고 클라이언트는 `node:crypto` 를 쓸 수 없다**(`override.test.mjs` 가 워커 import 그래프에서
  `node:` 를 금지한다). `crypto.subtle` 로 HMAC-SHA-256·SHA-256 을 쓴다 — 저장소 선례는
  `admin-auth.mjs:9` 와 `vocab-api.mjs:481`. `await import('node:crypto')` 는 정규식을 피해 가지만
  런타임에서 깨진다(테스트 초록 + 배포 성공 + **운영만 500**).
- **타임아웃을 반드시 건다.** 이 워커의 외부 `fetch` 중 타임아웃을 거는 것이 하나도 없다. 금고 PC 가
  "켜져 있지만 응답이 없는" 상태(절전·네트워크 반쪽)가 가장 흔한 고장이고, 타임아웃이 없으면 첫 금고에서
  요청이 매달려 두 번째로 넘어가지 못한다. 베낄 코드가 같은 저장소에 있다 —
  `crm/portal-api.mjs:71-78`(`AbortSignal.timeout` + 주입 가능 fetch).
  → *쓰기 1회에 외부 호출이 2~4회 나간다. 워커의 서브리퀘스트·CPU 한도 숫자는 저장소에 없으니
  Cloudflare 공식 문서에서 확인해 §출처에 남긴다(미확인).*

4. **국어 `state` 화이트리스트** — 지금은 알려진 누출(`wrong[].label`)만 겨냥해 뗀다. 절대규칙 4 가

   떨어뜨리면 학생 진도가 사라지므로 필드 목록을 먼저 확정해야 한다.

### A 를 코드로 강제한다 — `WB_ADMIN_ONLY`

설정만으로 "학생은 안 쓴다"고 두면, 주소가 한 번 새면 그때부터 조용히 갈라진다. 그래서
서버가 거부하게 했다.

```
WB_ADMIN_ONLY=1
```

- `/api/login` 과 `/api/login/status` 가 **403** 을 돌려준다. 토큰은 서명이 아니라 각 저장소에
  든 난수라, 워커가 내준 학생 토큰도 여기서는 검증되지 않는다 — **이 서버에 학생 기록이 생길
  길이 없다.**
- 관리 로그인·관리 웹은 그대로다. 관리 화면들이 학생 앱의 공용 로직 모듈(`/naesin/gen.js` ·
  `/chunk/lessons.js` · `/haru/plan.js` …)을 직접 불러 쓰기 때문에 **그 경로는 막지 않는다** —
  막으면 모드를 켠 순간 관리 웹이 깨진다.
- 기동 때 `[관리 전용]` 한 줄을 찍는다. 터널을 붙인 뒤 이 줄로 확인한다.
- `reading-server/admin-only.test.mjs` 가 양쪽 모드를 실제 HTTP 로 확인한다(거부·관리 웹 생존·

| 도메인 | **불필요** | **필수** (Cloudflare 에 zone 등록) |

Access 가 열리고, 덤으로 `wb-reading.whdudwns33.workers.dev` 대신 쓸 주소도 생긴다.
→ 원장 확인: 도메인은 이미 있다. **무료 요금제는 네임서버를 Cloudflare 로 옮기는 방식(full setup)만 된다** —
CNAME 부분 설정은 Business 이상이다. 옮기기 전에 등록처에서 DNSSEC 를 끄고, 그 도메인의 메일(MX)·홈페이지
레코드가 Cloudflare 로 다 넘어왔는지 확인한다. zone 이 Active 가 되기 전에는 터널 주소가 열리지 않는다.

## 4. 네임드 터널 — Windows 서비스로 (공식 문서 절차)

**고침(2026-10-12): 지금 Cloudflare 가 권하는 것은 원격 관리 터널(대시보드에서 만들고 토큰 하나로 설치)이고,
키트도 그 방식이다** — `reading-server/tunnel/README.md` 2~3단계. 대시보드 위치는 **Networking → Tunnels**,
설치는 관리자 CMD 에서 `cloudflared.exe service install <토큰>` 한 줄, 주소는 터널의 **Routes → Published
application** 에서 붙인다(DNS 레코드가 자동으로 생긴다). cloudflared **2026.7.3 이상**이면 토큰이 레지스트리가
아니라 `C:\ProgramData\cloudflared\token`(관리자·SYSTEM 만)에 들어간다 — 그보다 옛 버전은 서비스 실행 줄에
토큰이 평문으로 남는다(cloudflared RELEASE_NOTES 'VULN-143514'). 서비스 이름은 `Cloudflared`, 한 PC 에 하나뿐이다
— 금고 호스트가 생겨도 같은 터널에 경로를 더한다.

아래 로컬 관리 절차(cert.pem + config.yml)는 **대안으로만** 남긴다. `cert.pem` 은 그 계정의 **모든 터널을
만들고 지울 수 있는** 열쇠라(10년 유효) PC 에 두는 위험이 원격 관리 토큰(그 터널 하나만 돌릴 수 있다)보다 크다.
이 절차를 쓸 때도 순서는 **§5 의 Access 응용을 먼저 만들고 ④ DNS 연결을 맨 나중에** 한다 — 경로가 먼저 생기면
Access 를 걸 때까지 관리 화면이 인터넷에 그대로 열린다(Cloudflare 문서의 경고).

관리자 권한 CMD 에서. `<터널이름>`·`<터널ID>`·`wb.내도메인` 은 바꿔 넣는다.

```bat
rem ① cloudflared 를 C:\Cloudflared\bin\cloudflared.exe 로 두고 그 폴더에서 실행
cloudflared.exe service install
mkdir C:\Windows\System32\config\systemprofile\.cloudflared

rem ② 로그인 — 브라우저가 열리고 도메인을 고르면 cert.pem 이 받아진다
cloudflared.exe login
copy C:\Users\%USERNAME%\.cloudflared\cert.pem C:\Windows\System32\config\systemprofile\.cloudflared\cert.pem

rem ③ 터널 만들기 — <터널ID>.json 자격증명이 생긴다
cloudflared.exe tunnel create <터널이름>
copy C:\Users\%USERNAME%\.cloudflared\<터널ID>.json C:\Windows\System32\config\systemprofile\.cloudflared\<터널ID>.json

rem ④ DNS 연결
cloudflared.exe tunnel route dns <터널이름> wb.내도메인

rem ⑤ 규칙 검사 — --config 를 빼면 %USERPROFILE% 쪽 config.yml 을 검사한다(공식 문서도 같은 빈틈)
cloudflared.exe tunnel --config C:\Windows\System32\config\systemprofile\.cloudflared\config.yml ingress validate
```

`C:\Windows\System32\config\systemprofile\.cloudflared\config.yml`:

```yaml
tunnel: <터널ID>
credentials-file: C:\Windows\System32\config\systemprofile\.cloudflared\<터널ID>.json

ingress:
  - hostname: wb.내도메인
    service: http://127.0.0.1:8890   # 서버가 127.0.0.1 에만 묶인다(HOST) — localhost 는 Windows 에서 ::1 로 먼저 풀릴 수 있다
  - service: http_status:404
logfile: C:\Cloudflared\cloudflared.log
```

레지스트리 `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Cloudflared` 의 `ImagePath` 를
이 한 줄로 바꾼다(공백 하나만 틀려도 서비스가 안 뜬다):

```
C:\Cloudflared\bin\cloudflared.exe --config=C:\Windows\System32\config\systemprofile\.cloudflared\config.yml tunnel run
```

`sc start cloudflared` / 설정 바꾼 뒤엔 `sc stop cloudflared` → `sc start cloudflared`.
**Windows 는 cloudflared 가 자동 갱신되지 않는다** — 수동으로 올려야 한다.

### 서버는 실행기로 띄운다

**고침(2026-10-12):** `set` 으로 환경변수를 넣고 `server.mjs` 를 직접 띄우던 절차는 `WB_ADMIN_ONLY=1` 을 빠뜨리기 쉽고,
서버가 모든 주소(0.0.0.0)에 묶여 **터널·Access 를 거치지 않는 LAN 입구**가 남았다(`server.mjs` 의 listen 이 주소를 안 줬다).
지금은 `reading-server/tunnel/run-server.mjs` 가 저장소 밖 설정 파일(`C:\ProgramData\WB\server.env`)을 읽어
**관리 전용 + `HOST=127.0.0.1`** 을 강제하고(파일에 다르게 적혀 있으면 뜨지 않는다), 작업 스케줄러가 부팅 때 SYSTEM 으로
띄운다(`setup.mjs install-server`). `server.mjs` 는 `HOST` 를 받게 됐다 — 비우면 예전처럼 모든 주소다
(`reading-server/host-bind.test.mjs` 가 실제 소켓으로 확인한다).
작업이 SYSTEM 으로 돌리는 코드는 저장소가 아니라 **관리자 전용 사본**(`C:\ProgramData\WB\app`)이다 — 저장소는 일반 사용자도
고칠 수 있어서, 그 코드를 SYSTEM 으로 돌리면 파일 한 줄이 곧 SYSTEM 권한이다(설계 심사 2026-10-12). 설정 폴더·자료 폴더·사본은
주인을 관리자로 바꾸고 관리자·SYSTEM 만 남긴 뒤 실제 권한을 다시 읽어 확인한다.

관리 로그인이 없으면 서버가 뜨지 않는다(의도된 동작). **값을 저장소 파일이나 배치 파일에
적어 커밋하지 않는다** — 절대 규칙 1. 실행기는 설정 파일이 저장소 안에 있으면 거절한다.

## 5. 관리 웹에는 Cloudflare Access 를 같이 건다

터널만 붙이면 `/admin/*` 이 인터넷에서 열린다. 관리 PIN 한 겹뿐이고, 그 하나로 학생 기록 전체가
열린다. Zero Trust → **Access controls → Applications → Self-hosted and private** 로 `wb.내도메인` **호스트 전체**
(Path 비움)에 정책을 건다(허용: 원장·강사 이메일. 수단: 이메일 OTP 또는 Google).
**고침(2026-10-12):** 처음에 적었던 `/admin/*` 경로 정책은 그만둔다 — 아래 "호스트 전체" 가 A 안의 결론이고
키트도 그렇게 안내한다. 확인한 것 셋:
- **순서** — Access 응용을 **먼저** 만들고 터널 경로(DNS)는 맨 나중에. 반대로 하면 그 사이 관리 화면이 공개된다.
- **로그인 수단** — 새로 만든 Zero Trust 조직은 One-time PIN 이 자동으로 붙지 않고 기본이 "Cloudflare 계정
  구성원만"이다. Integrations → Identity providers 에서 One-time PIN 을 더하고 응용에서 그것을 골라야 강사가 들어온다.
- **정책 모양** — 이메일 목록은 **Include → Emails** 에 넣는다. Require 에 여러 이메일을 넣으면 AND 가 되어 아무도 못 들어온다.

그러면 관리 웹은 **Access 통과 → 관리 로그인** 두 겹이 된다. 무료 요금제는 **50명까지**로 확인했다
(cloudflare.com Zero Trust Access 가격 — "Free … teams under 50 users"). 한 번 로그인한 사람이 자리 하나를 쓰고
관리자가 지우기(Remove) 전까지 유지된다 — 퇴사한 강사는 Revoke 뒤 Remove 까지 한다.
가입 때 결제 수단을 물을 수 있으나 무료 요금제는 청구되지 않는다.

A 안에서는 **호스트 전체에 Access 를 걸어도 된다** — 학생이 이 주소를 쓰지 않으므로 원장·강사
이메일만 허용하면 끝이다. 그게 가장 단단하다.

**금고(§1.5)는 이 호스트에 두지 않는다.** 사람 정책이 걸린 호스트는 워커의 `fetch` 를 막는다 —
금고는 `ko-vault-a.내도메인` 처럼 **다른 호스트명**에 두고 사람 정책 없이 Access **Service Auth** 만
건다. 그래야 이 절의 "호스트 전체 Access" 가 그대로 산다.

### ingress 를 경로별로 쪼개지 말 것

cloudflared 의 ingress 규칙은 `path`(Go 정규식)로 경로를 가릴 수 있다. 그래서 "`/admin/` 만
통과"로 짜고 싶어지는데, **권하지 않는다.** 관리 화면이 학생 앱의 공용 모듈을 불러 쓰므로
허용목록에 그 경로들을 전부 적어야 하고, 관리 화면에 모듈이 하나 추가되는 날 **그 화면만
조용히 깨진다**(원인을 찾기 어려운 쪽의 고장이다). 경계는 `WB_ADMIN_ONLY` 가 코드로 지키게 두고
ingress 는 호스트 하나 → `http://127.0.0.1:8890` + catch-all 404 로 단순하게 둔다.

## 6. 남는 위험 — 터널을 켜기 전에 읽는다

- **라이선스 자료.** `db.json` 에 이그잼포유 팩·교재 코칭 원문이 산다. 터널은 그 디스크를 외부
  요청에 연결하는 일이다. 인증은 그대로 걸리지만 노출면이 원내 LAN → 인터넷으로 넓어진다.
  A 안 + 호스트 전체 Access 로 두면 그 면이 원장·강사 이메일로 좁혀진다.
- **가용성.** PC 가 꺼지거나 집·학원 인터넷이 끊기면 그 주소는 죽는다. A 안에서는 관리 웹만
  못 쓰는 것이라 수업은 멈추지 않는다 — B 안이면 정전이 곧 수업 중단이다.
  **A.5 금고는 그 사이다.** 학생 기록은 KV 라 진로독서·워드브레인·그 밖의 앱은 멈추지 않지만,
  **국어 단원은 금고 둘 다 꺼져 있으면 아무도 못 연다**(학생 기기 사본을 두지 않기로 했다 —
  원장 결정). 체험 팩으로 연습은 되고, PC 를 켜면 학생이 다시 누르지 않아도 올라온다
  (30초·2분·10분·30분 재시도). 2대를 집·학원에 둔 것이 이 창을 좁히는 장치다.
- **백업.** `db.json` 파일 하나가 전부다. `/api/admin/backup-now` 와 `listBackups` 가 있지만
  **같은 디스크에 쌓인다** — 디스크가 죽으면 같이 죽는다. 이관할 거면 외부 백업을 먼저 정한다.
  **금고 백업은 NAS 다**(원장 결정). 클라우드 동기화 폴더는 쓰지 않는다 — KV 에서 뺀 자료를 두 번째
  제3자 클라우드에 다시 상시 복제하는 일이 되고, 금고를 만든 이유가 그 자리에서 무효가 된다.
- **자동 갱신 없음.** Windows cloudflared 는 수동 업데이트다. 분기마다 올릴 사람을 정한다.
  Cloudflare 는 최신 릴리스에서 1년 안의 버전만 지원한다.
- **LAN 입구 — 고쳤다(2026-10-12).** 서버가 모든 주소에 묶여 같은 와이파이의 기기가 터널·Access 없이
  `http://<PC>:8890/admin` 에 닿았다. 실행기가 `HOST=127.0.0.1` 을 강제하고 `setup.mjs doctor` 가 LAN 주소로
  실제 연결해 보고 열려 있으면 실패로 잡는다.
- **"Healthy" 는 서버가 살았다는 뜻이 아니다.** 대시보드의 터널 상태는 cloudflared 가 Cloudflare 에 붙었는지만
  말한다 — 서버가 죽어도 Healthy 로 보인다(방문자는 502). 판단은 `doctor` 로 한다.
