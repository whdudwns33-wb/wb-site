## 0. 한 줄 요약

- **A · 운영 관점 — SOP 콕핏(직원의 하루를 런북으로 표준화)**: 직원의 하루를 런북 팩(슬롯·단계·판단 기준·공식 링크 키)으로 고정해 기존 업무지시서 task로 발행하고 강사·원장·카톡 요청을 요청함 하나로 모으되, 자료 1건의 보유·구매·제공은 B 원장에 맡기고 A는 "언제 자료 일을 했는가"의 체크만 갖는다.
- **B · 자산 관점 — 자산 원장(자료·좌석·구독을 공급망으로 관리)**: 이그잼포유 자료를 시작으로 학원이 산 자산의 라이프사이클을 task 자산 탭 원장에 기록하되, 시험일은 consult `academic_event`를 참조만 하고 `need_sets`는 학교↔교과서↔학년↔과 매핑과 `requiredSeries`만 정본화한다.
- **C · 성과 관점 — 수행 신호 관제(학생 수행 신호가 오늘 할 일을 만든다)**: 업무지시서 앱에 수행 탭을 얹어 재원생×프로그램의 일일 수행 상태(프로그램별 확인 스탬프 + 예외만 기록)로 신호를 판정하고, 그 신호가 담당 직원의 조치 카드를 만들며, 조치 종결 시간·미확인 비율·감사 불일치가 직원 KPI, 수행률은 센터 지표가 되는 관제.

세 안은 **"무엇을 관리하는가"** 가 다르다. A는 **직원의 절차**, B는 **자료·계정이라는 자산**, C는 **학생의 수행 결과**를 관리 대상으로 삼는다.
그래서 첫 화면의 단위, 새로 생기는 정본, 짓는 자리, 직원을 평가하는 숫자가 셋 다 다르다. 비교와 추천은 §6, 원장이 결정할 것은 §7.

## 1. 배경 & 전제 (세 안 공통)

### 1.1 요청

원장 요청 원문: "메타수학·넬트·스터디포스·클래스카드 같은 프로그램을 쓰고 있고, 이그잼포유·족보닷컴 같은 문제은행에서 자료를 받아
학생들에게 제공하고 있다. 이것들을 관리하는 직원을 두려 한다. 그 사람을 관리하고 편하게 작업할 수 있는 웹앱을 만들 것이다."

요구는 한 앱에 둘이다.

| 요구 | 쓰는 사람 | 뜻 |
|---|---|---|
| ① 편하게 일한다 | 새 직원(프로그램·자료 담당) | 외부 사이트 4곳과 문제은행 2곳을 오가며 확인·배정·구매·정리·제공·기록하는 일을 **덜 헤매고 덜 적게** 한다 |
| ② 그 사람을 관리한다 | 원장(+관리 담당) | 오늘 무엇이 끝났고 무엇이 막혔는지, 돈이 어디로 갔는지, 학생이 실제로 했는지가 **손으로 묻지 않아도 보인다** |

### 1.4 세 안이 공통으로 지키는 제약 (어기면 안 자체가 무효)

1. **라이선스 콘텐츠·학생 개인정보는 저장소·공개 오리진에 두지 않는다.** 앱은 메타데이터·코드·링크만. 파일은 드라이브(원장 계정)와 KV/D1 뒤에.
2. **외부 서비스는 공식 HTTPS 주소를 새 창으로 열 뿐이다.** 아이디·비밀번호·쿠키 저장, iframe, 스크래핑, 자동 로그인을 쓰지 않는다. 그래서 "수행 여부"는 사람이 외부 관리자 화면에서 보고 앱에 옮긴다 — 이 옮김을 얼마나 가볍게 만드는가가 세 안의 공통 과제다.
3. **이원화·이중 입력 금지.** 학생 등록·퇴원·연락처·수납은 아카플로우, 학생에게 한 일은 업무지시서 앱. 같은 값을 두 곳에 적지 않고, 새로 생기는 데이터마다 정본이 어디인지 적는다.
4. **하우스 스타일.** vanilla HTML/CSS/JS, 순수 로직은 `*-core.js` + `.test.cjs`, 외부 의존성 없음. 서버 응답 래핑 계약 유지.
5. **직원 한 명이 대상이다.** 관리 화면은 원장·관리 담당 둘이 본다. 대기업식 워크플로 엔진이 아니라, 지금 있는 지시서·요청 원장·경보 패턴을 재사용해 **첫 2주 안에 쓰기 시작**할 수 있어야 한다.

## 3. 제안 A. SOP 콕핏 — 운영 관점: 직원의 하루를 런북으로 표준화한다

> 관점 A(운영·절차). 관리 대상은 **직원의 업무 절차**다. 질문은 하나 — "이 직원이 오늘 해야 할 일이 정해진 순서와 기준으로 끝났는가." 학생이 실제로 했는가(→ 관점 C), 자료를 무엇을·얼마에 샀는가(→ 관점 B)는 이 안의 범위 밖이다.

### A.0 한 줄 요약

새 직원의 하루를 **런북 팩**(`task/runbook-pack.json` — 시간대 슬롯 + 단계 + 판단 기준 + 공식 링크 키)으로 고정해 기존 업무지시서 task로 발행하고, 강사·원장·카톡에서 들어오는 일은 **요청함**(`/ops-request`, D1 전용 원장) 한 곳으로 모아 접수→처리→결과를 남긴다. 원장은 슬롯 완료율·정시율·막힘·요청 소요와 **오늘 결과 타임라인**만 본다. 담당 직원은 **staff 권한 그대로**(manager 승격 없음), 학생 식별자는 SF 코드·stable studentId만, 학생별 수행 판정은 코워크가, 자료 파일은 드라이브가, 무엇을 샀는가는 B 원장이 정본이다. 새 코드는 `runbook-core.js`(+테스트)·`shared/external-links.js`·`sync/ops-request.js`(+테스트) 셋이다.

### A.1 이 관점이 보는 문제

| 대상 | Pain Point | 이 안이 주는 것 |
|---|---|---|
| **새 직원** | 프로그램 6종의 관리자 화면이 전부 다르고 "오늘 무엇을 어느 순서로"가 머릿속·카톡에만 있다. 인수인계가 사람에 붙어 있다. | 오늘 런북 한 블록. 슬롯을 열면 단계·판단 기준·공식 링크가 함께 나오고 정상 완료는 체크만으로 끝난다. 절차가 `runbook-pack.json`에 남아 사람이 바뀌어도 이어진다. |
| **원장** | "했다"는 말만 있고 언제·무엇을·어디까지인지 볼 수 없다. 카톡 요청 누락을 모른다. 평가가 인상 평가다. | 슬롯 정시 완료율, 요청 소요 중위값, 막힘 리드타임, 결과 타임라인(슬롯별 outcome·건수·메모·링크 한 줄). "절차를 지켰는가"가 숫자와 한 줄 기록으로 남는다. |
| **강사·관리 담당** | 계정 발급·세트·문제지를 카톡·구두로 던지고 답이 왔는지 다시 묻는다. | 강사 개인 링크에서 [＋ 운영 요청] → 상태(접수·처리중·완료·막힘)와 결과 링크가 보인다. 다시 묻지 않는다. |
| **학생·학부모** | (간접) 문제지·자료가 언제 나오는지, 계정이 열렸는지 모른다. | 처리 지연이 줄어든다. 학생·학부모가 쓰는 새 화면은 **만들지 않는다**. consult 요청 큐는 Phase 2 교차 앱 읽기 전까지 원장 화면에서만 보인다. |

### A.2 관리 대상과 화면의 첫 단위

"관리"는 **절차의 이행**을 관리하는 것이다. 첫 화면의 단위는 학생 카드도 자료 카드도 아닌 **오늘의 런북 슬롯**이다. 직원 개인 링크의 기존 `오늘` 화면 상단에 두 블록이 얹힌다(Phase 1은 새 탭·새 파일 없이 `index.html` 함수 추가).

| 블록 | 카드 내용 | 정렬·표시 |
|---|---|---|
| **① 오늘의 런북** | 시각·제목·단계 n/m·상태(⬜🔸✅🚧)·`↗` 외부 링크 버튼·`⚠ 이월` 배지 | `slotTime` 오름차순. `time+window` 지난 미완료는 상단 빨간 테두리. `__att__<staffId>` 기록이 없으면 블록 머리에 "출근 체크 먼저" 배지(읽기 전용, 출퇴근 정본은 `/staff-attendance`) |
| **② 내 요청함** | `assigneeId === 본인`인 요청만. 종류·프로그램·대상 코드·필요일·상태·[접수][완료][막힘] | `neededBy` 오름차순, 오늘 마감 상단 |

슬롯이 곧 지시서다 — 기존 task에 `kind:'runbook'`과 `runbookSlotId`를 붙인 것이라 직원은 이미 아는 체크·메모·막힘 UI를 그대로 쓴다. 슬롯의 `guide`는 기존 "📘 이렇게 하세요" 자리에 나오고, `ext` 키가 있는 단계에는 [↗ 스터디포스 관리자 열기] 버튼이 붙는다.

### A.4 원장의 관리 — 감독·확인

원장은 **직원 현황 탭 → 운영 카드 + 오늘 결과 타임라인**을 본다. 학생 이름·연락처는 어디에도 없다.

| 무엇을 보나 | 어떻게 계산하나 | 무엇을 결정하나 |
|---|---|---|
| 런북 완료율 | `done / 발행` — 분모는 **`kind:'runbook'`만**(직원 추가 업무·일반 지시 제외) | — |
| 정시율 | `time + window` 안 done 비율(`window` 기본 60분, 슬롯별). 기기 시각 기준, 서버 `srv_at`과 15분 이상 어긋나면 "표본 이상" 표시 | window·슬롯 시각 조정 |
| 지연·막힘 | 런북 task는 `time+window` 이후에만 overdue(`alertsToday()` 수정). 🚧 막힘은 사유와 함께 상단 | 막힘에 관리자 지시로 회신 |
| 요청 소요 | 요청자 기준 `createdAt→doneAt`(KPI), 작업 기준 `acceptedAt→doneAt`(참고) 중위·최대. `neededBy` 전 완료 비율 | SLA 확정 |
| 이월 잔량 | `⚠` 배지 수, 3일+ 이월 | 슬롯 폐기·분할 |
| **오늘 결과 타임라인** | 슬롯 시각·outcome·cnt·note 한 줄씩 + 요청 완료 건(resultUrl 포함). 각 줄에 [대조 완료] 1탭(주 1회 무작위 대조 증적, `checks` `__audit__<taskId>|<date>`) | 형식 체크 여부 |
| 주간 절차 리포트 | **원장이 월요일 첫 접속 시 클라이언트가 조립**(캐시 없음, 서버 cron은 Phase 2) — 슬롯별 완료/정시/막힘, 요청 종류별 건수·소요, 카톡 경유 비율. 첫 줄 고정 문구 "절차 지표이며 학습 결과가 아님" | 팩 개정 |

**자동으로 올라오는 것**: 기존 탭 빨간 숫자(막힘 + window 지난 미완료), 기존 "오늘 마감 브리핑"에 운영 절(슬롯 완료율 + 직원 슬롯 `note` 포함 — `briefText` 수정). 새 알림은 없다.

**직원 평가 근거**는 위 숫자와 타임라인이다. 막힘 신고는 감점이 아니라 **가점**(막힘을 숨기면 절차 결함을 알 수 없다). 원장이 절차를 고쳤는가는 Phase 0~1에서는 지시 목록 관리의 수정·중단 이력, Phase 2부터 `packVersion` 이력으로 본다.

### A.7 기술 설계

**어디에 짓는가 — task/ 앱 안.** README 7-4 기준 ① 쓰는 사람: 담당 직원·강사·원장·관리 담당 = 업무지시서 사용자 ② 백엔드: sync D1 ③ 핵심 기능: 지시서 발행·체크. 분리 조건 1(학생·학부모)·2(무거운 데이터)에 걸리지 않는다. 조건 3(400KB)은 이미 1.47MB로 깨져 있으나, Phase 1은 **새 파일 없이 함수 추가**로 들어가고 지연 로딩(`document.createElement('script')`로 `runbook-ui.js?v=…` 동적 삽입, 실패 시 기존 화면 폴백 — task 앱은 Pages 배포로 `?v=` 수동 캐시버스팅)은 Phase 2 과제로 둔다. 직원 가이드북 "시스템 2개"도 유지된다.

**권한 결정 — manager 승격 철회.** manager는 `session.isAdmin`이 되어 원장 탭 전부와 학생·보호자 연락처 편집(`openLessonBriefingEditor`)까지 열린다. 대신 own 스코프 규칙(tasks 행은 `owner === auth.id`만)을 그대로 두고, 요청은 `/ops-request`가 역할별로 필터한다: 강사 staff는 `create`·본인 요청 조회, 담당 직원 staff는 `assigneeId === 본인` 조회·`accept/done/block`, admin/manager는 전체·`assign`·`cancel`. `/teacher-live-request`의 recipient 모델과 같다.

**재사용 자산**: task 모델·4단계·이월·빨간 숫자·`#add=`·관리자 지시(막힘 회신)·마감 브리핑·신규 학생 탭·교재 탭 주문·CAS 패턴·`/teacher-live-request` 구조·consult URL 상수.

### A.9 KPI

**직원 개인 KPI**(주간, 분모는 `kind:'runbook'`만)

| KPI | 정의 | 측정·목표 |
|---|---|---|
| 런북 완료율 | done / 발행 | `checks`, 95% |

| 요청 소요 | median(`doneAt − createdAt`) | 계정·배정 ≤1영업일, 문제지 다음 수요일 |
| SLA 준수율 | `doneAt ≤ neededBy` | 90% |
| 막힘 적시성 | 막힘 중 `time+window` 안 신고 비율 | 가점 |

## 4. 제안 B. 자산 원장(ledger) — 자산 관점: 자료·좌석·구독을 공급망으로 관리한다

> 관점 B(자산·비용·라이선스). 관리 대상은 **학원이 돈을 내고 산 자산**이다 — 자료 파일·프로그램 좌석·구독. 질문은 하나 — "산 것이 어디에 있고, 실제로 쓰였고, 얼마가 나갔는가." 직원의 절차(→ 관점 A)와 학생의 수행(→ 관점 C)은 이 안의 범위 밖이다.
> 사실 근거: `task/README.md` 7-3~7-5, `sync/README.md` `/sync`·`/roster`·`/book-issue`, `naesin/README.md` 팩 파이프라인·인테이크 규칙, `docs/운영체계/이원화-아키텍처-설계서.md` §2·§3.2·§4, `task/index.html` `ownerOfCheck`·`__opset__`·`__op__`, `consult/index.html` `academic_event`(시험일 정본), `sync/schema.sql` `tasks(app, data)`, `sync/worker-core.js` 권한 판정·LWW upsert. 브리프에 없는 것은 "(가정)".

### B.0 한 줄 요약

메타수학·넬트·스터디포스·클래스카드의 **좌석(계정)**, 이그잼포유·족보닷컴의 **자료 파일**, 그 둘의 **구독·결제**는 전부 학원이 돈을 내고 산 **자산**이다. 새 직원은 이 자산의 관리인이고, 앱은 자산 하나의 라이프사이클(필요 산출 → 구매 요청 → 승인 → 구매·등록 → 배정 → 제공 → 회수/만료)을 기록하는 **원장(ledger)** 이다. 파일은 드라이브에, 학생은 stable `studentId`로, 앱에는 메타데이터·링크·이벤트만 둔다. 이미 D1에 있는 교재 원장(`/book-order`·`/book-issue`)이 첫 사례이며 이 안은 그것을 "교재 → 모든 자산"으로 일반화한다. **단, Phase 0~1은 이그잼포유 자료(`material`) 하나만 짓는다** — 좌석·구독·족보닷컴은 과금 단위와 라이선스가 가정 위에 있어 원장 결정(B.12) 뒤 Phase 2에 붙인다.

### B.1 이 관점이 보는 문제

| 대상 | Pain Point | 이 안이 주는 것 |
|---|---|---|
| 새 직원 | 무엇을 사야 하는지 매번 묻고, 산 파일을 어디에 어떤 이름으로 둘지 헷갈리며, 이미 산 것을 다시 산다 | 시험 범위를 넣으면 **필요 자료 목록이 산출**되고 보유분은 걸러진다. 승인된 건은 **구매 지시서**로 내려오고 그 `detail`에 인테이크 폴더·파일명이 적혀 있다. 이그잼포유 미출간·결제 한도 같은 막힘은 지시서 🚧로 올리면 자산 행에 `blocked`로 남는다 |
| 원장 | 월 얼마가 어디로 나가는지, 산 자료가 실제로 팩·인쇄까지 갔는지 모른다. 결제는 카드 명세서로만 확인 | 승인 대기 큐·갭 표·**"산 채로 잠자는 자료"** 가 뜬다. **승인 전 결제는 규율로 금지**하고(앱은 외부 결제를 막을 수 없다), `requested` 없는 `purchase`는 사후 경고로 잡는다 |
| 강사 | 이 단원 자료가 이미 있는지, 어느 폴더인지 모른다 | 카탈로그에서 교과서·학년·과로 검색 → 있으면 보기 링크·파생 packId, 없으면 **자료 요청** 한 번 |
| 학생·학부모 | (이 안은 학생 화면을 만들지 않는다) 어떤 자료를 언제 받았는지 근거가 없다 | 제공 이벤트가 시험 범위 단위로 남아 "이 시험에 무엇을 어떤 경로로 제공했나"를 답한다 |

**이 안이 보지 않는 것과 그 일이 이뤄지는 기존 화면**(범위 밖 → 다른 안):

| 직원 업무(브리프 §3) | 이 안 | 실제로 하는 곳 |
|---|---|---|
| 수행 확인(SF 13:00/20:30, 클래스카드 점검) | 범위 밖(→ C안) | 외부 관리자 페이지 + `_bus`(agent-studyforce-manager) |
| 주간 학습 횟수 | 범위 밖(→ C안) | task 원생 탭 `__op__` 모달(기존 그대로) |
| 클래스카드 세트·SF 과제·메타수학 문제지 배정 | 범위 밖(→ A안 절차) | 외부 사이트; 메타수학은 consult 수요일 큐 |
| SF 제본·지문정리노트 발주 | 범위 밖 | task 교재 탭 `family:'studyforce'`(기존, 변경 없음) |
| 일일 보고·막힘 | 지시서 막힘만 `blocked`로 역연결 | task 지시서(기존) |

### B.2 관리 대상과 화면의 첫 단위

**관리란 자산 목록(카탈로그)과 자산 상태(라이프사이클)를 정확하게 유지하는 일**이다. 첫 단위는 "오늘 할 일"이 아니라 **자산 행**이다.

| 종류 `kind` | 예 | 단위 | Phase |
|---|---|---|---|
| `material` | 이그잼포유 `[03] WORD TEST` 학생용 PDF | 파일 1개 | **0~1** |
| `seat` | 메타수학 학생 계정 1개, 클래스카드 1석, 넬트 응시권(가정: 회당 과금) | 계정·권 1개 | 2 (B.12-3·10 뒤) |
| `subscription` | 스터디포스 학생 구독(요금제 코드만), 메타수학 교실 계약(가정) | 결제 단위 | 2 (B.12-3 뒤) |

족보닷컴은 과·시리즈 개념이 없어 이그잼포유 카탈로그 키에 맞지 않는다 — B.12-4 결론 전까지 카탈로그에 넣지 않는다. SF 제본·노트는 교재 발주 원장에 남기고 자산 원장의 SF는 구독 좌석만이다.

상태 `status`(material 기준 확정): `needed → requested → approved → purchased → registered → assigned → provided → revoked`, 거절 `rejected`. **[등록] 한 번이 `purchase`+`register` 두 이벤트를 찍는다**(외부 결제와 드라이브 업로드는 한 자리에서 일어나므로 클릭을 둘로 나누지 않는다). 좌석·구독 전이표는 Phase 2에 별표로 둔다.

**첫 화면(Phase 0) = 셋만**: ① 승인 대기 n건 ② 갭 표(시험 범위별 필요 – 보유 = 사야 할 것, 예상 금액) ③ 잠자는 자료(시험일 D-7인데 `registered`에서 정지 — 시험일은 consult `academic_event.examDate` 참조값, B.5). 월 지출·활용률·미사용 좌석·중복 카드는 해당 kind가 들어오는 Phase에 붙인다 — material만 있는 화면에서 빈 카드를 그리지 않는다.

### B.4 원장의 관리 — 감독·확인

| 원장이 보는 것 | 결정 | 자동으로 올라오는 것 |
|---|---|---|
| 승인 대기: 자산별 예상 단가(`PRICE_HINTS`)·합계·중복 여부·교사용 권장 근거 | [승인]/[반려] | 같은 카탈로그 키가 `purchased` 이상이면 **중복 경고**가 붙어 승인이 2단계 확인으로 바뀐다 |
| 갭 표 + 잠자는 자료 | 팩 제작 우선순위, 인쇄 여부 | 시험일 D-7 `registered` 정지 자산 |
| 오늘 원장 이벤트 요약(입력 0): 직원별 이벤트 수·`blocked` 사유·리드타임 | 막힘 해소(결제 수단·드라이브 권한) | `requested` 없는 `purchase`(규율 위반) 경고 |
| 감사 이력(append-only) | 이상 건 조사 | Phase 0은 이벤트 행 `__licev__`로, Phase 1은 D1 트리거로 불변 |
| 월 지출·활용률·미사용 좌석 | 다음 달 예산 | **Phase 2**(좌석·구독·팩 배포 확인 연동 뒤) |

원장 입력은 승인·반려·확인 셋뿐이다. 직원 평가 근거는 이벤트 시각 차이(`approve→register`, `register→assign`)에서 나오되 **`blocked` 구간은 시계를 멈춘다** — 미출간·결제·드라이브 권한은 직원 밖 요인이다. 개인 지표는 직원이 직접 쓰는 **Phase 1부터** 성립한다(Phase 0은 `byStaffId`가 관리 담당으로 찍힌다). 월 1회 "드라이브 파일 수 = 자산 수" 정합 감사는 하지 않는다 — 폴더에 `00_`·`99_` 등 원장 밖 파일이 섞여 구조적으로 불일치한다. 대신 자산 행의 `drivePath`를 [확인] 클릭으로 점검하는 `audit` 이벤트만 둔다.

**개인정보 경계.** 원장은 인증된 저장소(D1)에만 있고 정적 코드에는 코드표(교과서 10종, 시리즈 번호, `PRICE_HINTS`, 공식 URL)만 있다. `schoolCode`는 정규식으로 학교명 유입을 막고 매핑표는 D1에 둔다. `note`에는 "학생 이름·학교명 금지, 자산 id·과로 지칭" 가이드 문구와 서버 길이 제한을 `/book-issue reason`과 같은 방식으로 붙인다. SF 구독은 **학생 단위 금액을 저장하지 않고** 요금제 코드(`plan:'basic'`)만 두며 금액은 정적 코드표(149,000)로 표시한다. `SUB-SF-0NN`↔`studentId` 결합은 기본 **미결합**(SF 코드만, 좌석 수·만료 집계용)이고 결합 여부는 B.12-3에서 결정한다. 자산 행 삭제는 `deleted:true` 표시만(7-5: 키를 지우면 델타 동기화로 되살아난다).

**라이선스 범위 규칙.** 학생 제공 경로는 **팩·인쇄 둘**로 제한한다. 팩은 내신브레인이 학생 토큰·exam scope로 재원생만 받게 이미 막고(퇴원 시 `naesin:exam` 삭제), 인쇄는 부수가 원장에 남는다. **링크 채널은 원내 계정(강사)에게만** 쓴다 — "드라이브 링크 공유 금지"와 "학생에게 보기 전용 URL 제공"은 양립하지 않으며(막으면 학생 이메일을 모아야 하고, 허용하면 유출 경로가 된다), 학생 링크 제공과 그에 딸린 `expiresAt`·회수 목록·재원 대조는 B.12-5 결론 뒤 Phase 2다. 이그잼포유 라이선스 서면 확인은 `naesin/README.md`에 미결이며 `license` 기본값(가정: 원내 재원생 학습 목적 허용, 재배포 금지)은 결론에 따라 값만 바꾼다.

### B.12 이 안을 택하면 원장이 결정해야 할 것

1. **(Phase 0 착수 전)** 새 직원 권한 — Phase 0은 지시서만 받고 [등록]은 관리 담당이 하는 기본안인가, `TASK_MANAGER_STAFF_IDS`에 넣어 전체 현황·발행 권한까지 주는가. Phase 1은 `TASK_LEDGER_STAFF_IDS`(자산 쓰기만).

5. 학생에게 보기 전용 링크를 줄지 — 주려면 (i) 학생 이메일 수집(가정: 아카플로우에 없음) 또는 (ii) 링크 공유 허용+만료 기준(시험 +14일 기본) 중 하나.
6. **(Phase 0 착수 전)** 시험 범위 매핑 정본은 `need_sets`, 시험일 정본은 consult `academic_event`(기존 그대로), 내신브레인 시험 등록은 둘의 파생 — 이 방향에 동의하는가. Phase 0 동안 시험일을 consult에서 손으로 복사하고 범위를 naesin-admin에 다시 적는 것을 감수하는가.

8. 교재 원장(`/book-order`·`/book-issue`)을 Phase 2에 자산 종류로 흡수할지, 보호자 포털 계약 때문에 영구 분리할지.

## 5. 제안 C. 수행 신호 관제 — 성과 관점: 학생 수행 신호가 오늘 할 일을 만든다

> 관점 C(학생 결과·이탈 방지). 관리 대상은 직원의 절차(A)도, 자료·구독 자산(B)도 아니라 **학생 쪽에 결과가 생겼는가**다 — 프로그램을 실제로 했는가, 자료가 실제로 학생 손에 갔는가, 이탈 신호에 얼마나 빨리 대응했는가. 계정 발급·13:00 점검 절차의 표준화는 A안, 자료 구매·구독 비용·`planned→bought` 단계는 B안의 범위이며 이 안은 그 결과만 읽는다.

### C.0 한 줄 요약

업무지시서 앱(`task/`)에 **수행 탭**(`#perf`)을 지연 로딩으로 얹는다. 프로그램 담당 직원은 20:30에 외부 관리자 화면(공식 링크)을 보고 프로그램별 **확인 스탬프 1탭 + 미수행·부분 학생만 예외 탭**으로 기록한다. `perf-core.js`가 대상일 기준 연속 미수행·신규 미시작·미확인 누적·과제 미배정·넬트 추세를 판정해 담당 직원의 **조치 카드**(`contact/assign/teacher_note/nelt_notice`)를 만들고, 조치 `openedAt→closedAt` 소요·미확인 비율·감사 불일치가 직원 KPI, 주간 수행률은 센터 지표가 된다. 점수·정답률은 끝까지 앱에 넣지 않는다. 재원생 범위에서는 앱 기록이 정본이고 코워크 에이전트의 20:30 판정은 Phase 0 시작일에 중단한다 — 같은 값을 두 곳에 적지 않기 위해서다.

### C.1 이 관점이 보는 문제

| 대상 | Pain Point | 이 안이 주는 것 |
|---|---|---|
| 새 직원 | 4개 관리자 화면을 매일 돌며 확인은 했는데 "누구에게 무엇을 해야 하나"가 머릿속에만 남고 후속이 없다. 확인 결과를 에이전트 파일과 카톡에 따로 적는다 | 확인 결과를 스탬프+예외로 남기면 **후속 조치가 문구와 함께 자동 생성**된다. 기록 장소는 앱 하나 |
| 원장 | "관리 잘 하고 있어요" 외에 근거가 없다. 미수행 학생을 2주 뒤 퇴원 상담에서 처음 안다. 직원이 실제로 확인했는지 알 길이 없다 | 첫 3주부터 직원별 open/done/blocked 건수·오늘 미확인 셀·어제 P0 미종결이 카드 1장으로 뜬다. 평가 근거가 **대응 시간·미확인 비율·감사 불일치**로 고정된다 |
| 강사 | 자기 학생이 클래스카드를 열흘 안 한 것을 수업 중 학생 입에서 듣는다. 카드가 학생 수만큼 쏟아지면 무시한다 | 주 1장 `[전달] 이번 주 온라인 미수행 학생 n명` 지시서(steps=학생별)로 도착. P0만 개별 카드 |
| 학생·보호자 | 자료를 "줬다"는데 못 받았거나, "했다"는데 기록이 없다 | 자료는 `delivered` 시각이, 수행은 주간 `n/목표`가 남는다(포털 공개는 Phase 2 결정 사항) |

기존 원생 탭 ⚠️ 관심 필요 카드(`riskFlags/opRisk/examRisk`)가 부족한 것은 셋이다 — ① 단위가 **주간 횟수**(`__op__`)라 미수행을 최대 7일 늦게 안다, ② 경보가 떠도 **누가 무엇을 할지**가 없어 카드에서 끝난다, ③ 판정 규칙이 코워크 에이전트 문서에만 있어 사람이 입력한 값이 앱에 남지 않는다.

### C.2 관리 대상과 화면의 첫 단위

**관리 대상 = 재원생×프로그램의 "오늘 상태"와 그것이 만든 "조치"의 종결.** 직원의 절차가 잘 돌았는지는 묻지 않는다.

**모집단(못 박는 규칙)**

| 집합 | 정본 | 판정 주체 | 겹침 |
|---|---|---|---|
| 재원생 × 이용 프로그램 | D1 private roster(아카플로우 유래) × `__perfset__` | **이 앱** | — |
| 비재원 스터디포스 구독생 | 구독 엑셀 | agent-studyforce-manager(그대로) | 재원+구독 병행 학생은 **앱**이 판정하고 에이전트는 결제 대조만 — 두 집합은 겹치지 않는다 |

첫 화면은 위아래 두 단이다.

**① 신호판(주간 격자)** — 행 = 담당 범위의 재원생, 열 = `스터디포스 · 클래스카드 · 넬트 · 메타수학 · 자료`. 스터디포스·클래스카드 셀은 이번 주 7칸 점(●완료 ◐부분 ○미수행 ?미확인 ·비대상 A결석), 배경은 신호 강도. 넬트 열은 `examTrend` ▲▼―와 마지막 응시 후 경과일. **메타수학 열은 링크와 `__exam__` 단계 추세만** — 일일 수행은 consult 학생 완료 기록이 정본이라 앱에 적지 않는다. 자료 열은 `delivered` 배지와 consult 자료 요청함 건수 링크(Phase 1).

| 셀 요소 | 값 | 출처 |
|---|---|---|
| 일일 점 | `dayState()` 파생 6값 `completed/partial/not_completed/unknown/not_due/absent` | `__perfday__` + `__perfset__.dueDays` + `__st__` |
| 주간 수행 | `min(daysDone,target)/target` | `perf-core.weekSummary()` |
| 넬트 추세·경과 | ▲▼― · D+n | `__exam__<name>`을 `resolveStudent()`로 해석 |
| 자료 배지 | `delivered` 시각 | `__mat__` (Phase 1) |
| 신호 배지 | 규칙 ID + P등급 | `perf-core.signals()` |

**② 조치 큐** — 자동 생성분만 담는다. 카드 = `유형 · 학생 · 근거(규칙, 대상일 며칠째) · 문구 · [완료/막힘/건너뜀]`. 수동 요청은 새 버튼이 아니라 기존 **관리담당 통합 요청함**에 `kind:'perf_action'` 행으로 들어오고(Phase 1), 관리 담당이 요청함에서 [조치로 전환]하는 순간에만 `__act__`가 생긴다 — 큐가 두 개 되지 않게 한다.

### C.3 직원의 하루 — 편하게 일하기

프로그램 담당 1명(관리 담당 롤, C.7)을 가정한다. 재원생 30명, 스터디포스·클래스카드 대상일 월~금, 미수행 하루 평균 5명.

| 시각 | 하는 일 | 화면 | 탭 |
|---|---|---|---|
| 09:30 | 어제 20:30 저장으로 생긴 조치가 정렬돼 있다(P0 2·P1 4) | 수행 탭 배지 `조치 6` | 0 |
| 09:40 | P0 `contact` 학생A(스터디포스 대상일 7일 연속 미수행). 문구 상수를 보고 보호자에 전화. [완료]가 `/contact-log`를 `type:'call', note:'SF 7일 미수행 안내'`(앱 생성)로 열고, 저장된 id를 `__act__.ctRef`에 넣어 `done` | 조치 카드 → 연락 모달 | 2/건 |
| 10:00 | P1 `contact`는 `type:'msg'`로 같은 흐름. 받지 못한 전화는 `result:'no_answer'`로 열어둔 채 이월 | 조치 카드 | 2/건 |
| 10:30 | `assign` 카드(어제 `why:'no_assignment'`): 클래스카드 관리자 화면(공식 링크)에서 세트 배정 후 [완료]. 배정 내용 결정이 필요하면 [강사 확인 요청]→`teacher_note`로 전환 | 카드 🔗 + [완료] | 1/건 |
| 11:00 | 신규생: `__onboarding__` 항목 '프로그램 계정·첫 과제 배정' 완료 여부는 그 원장이 정본. 앱은 미완료면 신호판 행에 `신규` 배지만 | 신호판 | 0 |
| 13:00 | 13:00 절차(계정 사용 가능·당일 과제 존재)는 **A안 범위** — 이 앱은 기록하지 않는다. 결과가 미배정이면 20:30 예외 입력의 `why`로 들어온다 | — | 0 |
| 20:30 | 스터디포스 관리자 화면을 이름순으로 훑고 신호판 "오늘 열"에서 **[확인 스탬프]** 1탭(`basis` 칩: `login_log/assignment_status/report`), 미수행·부분 학생만 `○/◐` + `why` 칩. 클래스카드 반복. 못 찾은 학생은 `?`로 명시 | 오늘 열 입력 모드 | 스탬프 2 + 예외 5×2×2 ≈ 22 |

| 주 1회 | 보호자 주간 카톡은 `weekSummary()` 값(n/목표)을 그대로 쓴다 — 예전 `__op__` 주간 숫자 입력은 하지 않는다 | 원생 카드 | 0 |
| 막힘 | 어떤 카드든 [막힘] → `st:'blocked'`, 원장 탭 빨간 숫자에 기존 막힘과 합산 | 조치 카드 | 1 |

**하루 합계(가정)**: 탭 30~40회, 관리자 화면 대조 포함 20~25분, 순회 사이트 2개(넬트·메타수학은 매일 열지 않음). 예전 `__op__` 주 1회 입력 대비 늘어나는 것은 "예외 학생 탭"뿐이며, 스탬프가 있어야 `unknown`과 "안 봤음"이 구분된다.

`no_assignment`의 조치 대상: 스터디포스·클래스카드 → `assign`(프로그램 담당 본인), 내용 결정 필요 시 `teacher_note`. 메타수학 문제지는 원장이 consult 수요일 큐에서 배정하므로 앱에는 큐 **링크**만 두고 조치를 만들지 않는다.

### C.4 원장의 관리 — 감독·확인

원장은 입력하지 않는다.

**Phase 0에서 보는 것(원장 카드 1장, 기존 직원 현황 카드 자리)**: 직원별 조치 `open/done/blocked/skipped` 건수, 오늘 프로그램별 스탬프 유무와 명시 `unknown` 셀 수, 어제 P0 미종결 수, 24h 초과 P0 목록. `perf-core.kpi()` 최소판.

**Phase 1 결과 보드**

| 지표 | 정의 | 원장의 결정 |
|---|---|---|
| 주간 수행률(센터 지표) | 학생별 `min(daysDone,target)/target`의 평균, 프로그램·강사별. `unknown`은 분모에서 뺀다 | 반 간 격차 30pp 이상이면 강사 면담 |
| 신호→대응 소요 | `openedAt→closedAt` 중앙값, P0/P1 분리 | 24h 초과 P0가 있으면 직접 개입 |
| 미확인 비율 | 대상일 셀 중 스탬프 없음+명시 `unknown` | 20% 넘으면 인력·순서 조정 |
| 2주 재발률 | `done` 후 14일 내 같은 규칙 재발 비율 | 높으면 임계치·문구 조정 |
| 넬트 하락·정체 대응률 | `examRisk` 학생 중 `teacher_note` 종결 비율 | 재배정 여부(승인 요청 지시서로 받음) |
| 감사 불일치 | 월 1회 원장이 무작위 5셀을 관리자 화면에서 직접 대조, 결과만 `__act__ type:'audit', result:'match/mismatch'`로 기록(캡처 없음) | 불일치 1건 이상이면 면담 |
| 자료 D-7 미달(Phase 2) | D-7에 `delivered` 없는 배정 학생 수 | — |

**자동으로 올라오는 것**: P0 생성 즉시 원장 탭 빨간 숫자, `blocked` 조치, 같은 학생 3주 연속 신호, `openedAt`이 바뀐 조치(이력 표시). 원장 승인이 필요한 것은 Phase 1에서는 **없다** — `reassign/zone_place`가 필요하면 조치 카드가 원장에게 `[승인 요청] 학생B 학습존 배치` 지시서 1건을 만들고 끝낸다. 승인 흐름 자체는 Phase 2.

**직원 평가 근거**는 직원이 통제하는 세 숫자만이다: 대응 소요(P0 24h·P1 48h), 미확인 비율, 감사 불일치. 수행률은 학생·강사·보호자 행동의 결과라 개인 KPI에서 뺀다. 입력 건수도 KPI가 아니다.

### C.5 정보 구조·데이터 모델

전부 `checks` 테이블의 `__prefix__<id>|<scope>` 키다. **기존 `__opset__/__op__/__exam__`은 학생 이름 키(레거시)** 이므로 이 안은 그 프리픽스에 새로 기록하지 않고 studentId 키를 신설한다. 서버 마이그레이션은 없지만 **클라이언트 데이터 이관 1회가 있다**(아래).

| 키 | 값 | 설명 |
|---|---|---|
| `__perfset__<studentId>\|all` (신규) | `{progs:['스터디포스','클래스카드'], dueDays:{스터디포스:[1,2,3,4,5], 클래스카드:[1,2,3,4,5]}, target:{…}\|null, from:'legacy'\|'bulk'}` | 이용 프로그램·대상 요일. `target`이 null이면 `PERF_DEFAULT_TARGET`(스터디포스 5·클래스카드 5) 적용, 학생별 override는 Phase 1. Phase 0 일괄 설정 화면이 레거시 `__opset__<name>`을 roster name→id로 자동 채운 뒤 원장이 확인·저장 |
| `__perfday__<prog>\|<YYYY-MM-DD>` (신규) | `{stamp:{by, at, basis:'login_log'\|'assignment_status'\|'report'}, ex:{<studentId>:{st:'not_completed'\|'partial'\|'unknown', why:'no_login'\|'no_assignment'\|'account_issue'\|'score_below_target'\|'review_pending'\|'other'}}}` | 일일 수행 정본. **스탬프 있음 + 예외에 없음 = completed.** 스탬프 없음 = 전원 `unknown`(저장 안 함). 연 730행으로 학생×365보다 작다. `time_short`·`absent`는 뺐다 — 결석은 `__st__` A에서 파생 |
| `__act__<staffId>\|<actionId>` (신규) | `{studentId, type:'contact'\|'assign'\|'teacher_note'\|'nelt_notice'\|'audit', rule:'S1', priority:'P0'\|'P1', evidence:{prog, dueStreak, from, to}, st:'open'\|'done'\|'blocked'\|'skipped', openedAt, closedAt, result:null\|'reached'\|'no_answer'\|'match'\|'mismatch', ctRef, taskRef, hist:[{st,at,by}]}` | `actionId = '<rule>:<prog>:<studentId>:<openedDate>'` — 두 기기가 같은 저녁 저장해도 같은 행으로 합쳐진다. `openedAt`은 병합 시 최솟값 유지. `result`는 `contact`(reached/no_answer)·`audit`에만 |
| `__mat__<studentId>\|<examRef>` (Phase 1) | `{items:[{kind:'exam4you_print'\|'jokbo_print'\|'link'\|'naesin_pack', ref, deliveredAt, by}]}` | **`delivered` 이벤트 하나**. `ref`는 packId 또는 교과서코드-학년-과. 학교명·파일명·가격·URL 없음. 카탈로그 교재는 book-issue `handed`가 정본이라 여기 적지 않는다 |
| `__op__<name>\|<monday>` (레거시) | — | **컷오버 규칙**: `__perfset__`이 있는 학생은 opModal 숫자 입력을 잠그고 온라인 프로그램 카드가 `weekSummary()`를 표시한다. 없는 학생만 옛 경로 |

**정본 표**

| 데이터 | 정본 | 읽는 곳 | 비고 |
|---|---|---|---|
| 학생이 누구인가 | 아카플로우 → D1 private roster | 신호판 행 | 앱은 `studentId`만. 이름 키 레거시는 `perf-core.resolveStudent(roster, nameOrId)`로 한 번 해석(동명이인은 `ambiguous` 반환·수동 매핑) |
| 이용 프로그램·대상일·목표 | `__perfset__` | 신호·수행률 | 구독 여부·금액은 구독 엑셀(B안) |
| 일일 수행(스터디포스·클래스카드) | `__perfday__` | 신호·원장 카드·에이전트 회수 | 점수·정답률은 외부가 정본 |
| 메타수학 일일 수행·문제지 요청·배정 | consult 앱 | 링크만 | 앱에 열을 만들지 않는다 |
| 넬트·메타수학 단계 | `__exam__<name>`(레거시 키 유지) | 넬트 열 | 입력 게이트를 `session.isAdmin`→`authRole in ['admin','manager']`로 넓힌다 |
| 신규생 계정·첫 과제 | `__onboarding__<studentId>\|all` 항목 | 배지 | 항목 추가만, 앱은 읽기 |
| 조치와 종결 | `__act__` | 조치 큐·KPI | 연락 기록은 `/contact-log`(`type:'call'\|'msg'`)가 정본, 조치는 `ctRef` |
| 학생 요청 자료의 처리 | consult `material_request` | 건수·링크 | 가져오지 않음 |
| 선제 배포 자료 인계 | `__mat__` delivered | 자료 열 | 카탈로그 교재는 book-issue |
| 학습존 수행 | `[학습존]` task의 step 체크 | `src:'zone'` 파생 | 별도 입력 없음 |
| 학생 자기 체크 | student portal v3 | Phase 2 (가정) | 강사 지시서 활동에 `프로그램:클래스카드` 태그 + 학생 공개일 때만 근거로 표시 |

**개인정보 경계**: 새 키 어디에도 점수·백분위·학교명·전화번호·계정 ID·자유 메모가 없다. 모든 값은 닫힌 enum이고 `note`는 앱이 만든 상수 문구다. `SF-0NN`↔`studentId` 매핑은 앱에 두지 않고 코워크 PC 비공개 표에 둔다(가정, Q9).

### C.6 외부 서비스·자료와의 경계

| 대상 | 앱이 하는 것 | 앱이 절대 안 하는 것 |
|---|---|---|
| 스터디포스·클래스카드·메타수학·넬트 관리자 화면 | `PERF_LINKS` 상수(코드, 공식 HTTPS 4개 — 공개 오리진에 둬도 되는 주소, **PR 리뷰가 승인 절차**)를 신호판 상단 고정 링크 `target=_blank rel=noopener` | 아이디·비밀번호·쿠키 저장, iframe, 스크래핑, 자동 로그인, 화면 캡처 업로드 |
| 학생용 링크 | 포털 scope v2 방식 그대로 | 직원 앱에서 학생 계정으로 여는 행위 |
| 이그잼포유·족보닷컴 | `__mat__`에 `delivered`·`ref`만 | 파일·영수증·가격·URL 저장. 파일은 드라이브 `WB 교재스캔/…`, 팩은 KV |
| 라이선스 범위 | `delivered` 대상은 재원생 개인 제공 | 자료 파일을 포털·저장소에 올리는 것 |

"편함"은 링크가 아니라 **순서와 예외 입력**에서 나온다 — 입력 모드는 관리자 화면과 같은 이름순(가정)으로 학생을 세우고, 정상 수행 학생은 손대지 않는다.

**A안 Phase 0을 첫 주에 시작한다.** 이어서 A Phase 1(요청함)과 **B Phase 0(자산 탭, 자료만)** 을 2~5주차에 병행한다. **C는 Phase 2**로 두되, C의 20:30 스탬프는 런북 `R-2030-SF` 슬롯 안에 들어갈 자리를 처음부터 비워 둔다. 조합 원칙은 하나다 — **A가 뼈대(언제·어떤 순서로), B와 C는 그 슬롯의 내용(무엇을 확인·기록하나)** 이다.

### 왜 A로 시작하나

1. **직원 1명 채용이라는 상황.** 첫날부터 "오늘 무엇을 어느 순서로"가 있어야 한다. A Phase 0은 앱 코드 0줄, 팩 JSON 1개, 기존 `#add=` 발행으로 1주 안에 돈다. B는 관리 담당이 [등록]을 대신 눌러야 하고(7-3 제약), C는 착수 조건 결정 2개와 코워크 스킬 개정이 선행되어 최소 3주다. 사람이 출근하는 날짜에 맞춰 돌 수 있는 것은 A뿐이다.
2. **개인정보를 늘리지 않는다.** A는 학생 단위 기록을 하나도 새로 만들지 않는다(`targetRef`는 SF 코드·studentId만). B Phase 0~1은 `scope=exam`이라 학생 조회 자체가 없다. C는 재원생×프로그램×일 단위 기록을 만든다 — 셋 중 가장 민감하므로 가장 나중이 맞다.
3. **저장소 자산과 겹친다.** A의 `/ops-request`는 `sync/teacher-live-request.js`의 recipient 모델 복제, 런북 인스턴스는 기존 task 행이다. B의 `ledger-core.js`는 `asset-core.js`·`/book-issue` CAS 패턴 복제다. C의 `perf-panel.js`는 기존 패턴이 없는 로더 신설과 `__opset__` 이관이 붙는다. 신규 설계량이 A < B < C 순이다.
4. **결정적으로, A는 staff 권한을 유지하고 C는 manager 승격을 요구한다.** 관리 담당 롤은 전체 현황·지시서 발행·연락 현황 전체 열람을 연다. 갓 채용한 직원에게 첫날 그 권한을 주는 결정을 원장이 내리기 전까지 C는 시작할 수 없다. A를 먼저 돌리면 이 결정을 미룰 수 있다.

### 8.1 원장 결정 — "별도의 업무, 별도의 앱"
