# 파트너 학원 연계 — 기획서 v0 (2026-10-06)

웩슬러브레인센터와 지역 학원(수학·영어 등)이 **서로 광고·소개를 해 주고, 센터는 파트너가 보낸 가정에 검사를 제공**하는 연계 프로그램의 운영 설계와,
그것을 어디에 구현할지(세일즈데스크 통합 / 별도 앱)의 결정 근거. 코드는 `crm/`(세일즈데스크) 안의 파트너 모듈이다 — §6 참고.

> 정본 규칙: 파트너 학원의 실명·연락처·계약 조건은 저장소에 적지 않는다(앱의 D1 에만). 이 문서는 구조와 절차만 담는다.

## 1. 무엇을 하는가

| 방향 | 흐름 | 파트너에게 | 센터에게 |
|---|---|---|---|
| **파트너 → 센터** (들어오는 소개) | 파트너 학원이 자기 학생 가정에 센터 검사를 권하고 포털에서 소개를 보낸다 → 센터가 연락·예약·검사·해석 → 결과에 따라 학원·컨설팅 전환 | 학생 가정에 줄 혜택(검사비 할인 등)·자기 학원 신뢰도 | 검사 리드(가장 전환율 높은 채널 후보)·파트너별 전환 수치 |
| **센터 → 파트너** (나가는 소개) | 검사·해석 뒤 "수학 보강이 필요" 같은 판단이 나오면 가정 동의를 받고 맞는 파트너에게 소개 → 파트너가 연락·등록 여부를 포털에서 표시 | 검증된 상담 리드 | 가정에 줄 다음 단계·파트너와의 상호성(정산 근거) |
| **광고 교환** | 파트너 학원 안내물에 센터 검사 소개, 센터 안내물·브레인레터에 파트너 학원 소개 | — | — |

핵심 약속: **소개는 가정이 동의한 것만**, **파트너는 자기가 보낸(받은) 가정만 본다**, **정산은 숫자(가정 수·검사 완료·등록)로만** 한다.

## 2. 역할

- **원장**: 파트너 등록·조건 합의·링크 발급·정산 문구 발송·분기 리뷰. 파트너에게 보내는 소개를 승인한다(가정 동의 확인).
- **센터 직원(실장)**: 들어온 소개를 일반 리드와 같이 처리(연락 → 예약 → 검사 → 팔로업). 나가는 소개를 만든다(원장 확인 뒤).
- **파트너 학원(외부)**: 포털에서 소개를 보내고, 받은 소개의 진행 상태를 표시한다. 다른 정보는 보지 못한다.

## 3. 흐름

### 3.1 들어오는 소개(파트너 → 센터)
1. 파트너가 포털 `/partner/`(원장이 발급한 개인 링크)에서 **소개 보내기**: 보호자 이름·전화·아이 이름·학년·메모·**보호자 동의 체크**(필수).
2. 센터 세일즈데스크에 리드가 생긴다 — 채널 `파트너`, 파트너 이름이 붙고, 문의 원문에 "파트너 ○○ 소개"가 남는다. 오늘 화면의 "바로 연락할 문의"에 올라온다.
3. 이후는 일반 리드와 같다(예약·검사·해석·D+3/7/14 팔로업·판정). 파트너 포털에는 **거친 단계**(접수 → 예약 → 검사 완료 → 등록/종료)만 보인다.
4. HubSpot 연락처에는 `wb_source_channel=파트너`, `wb_partner=파트너 이름`이 간다(승인 큐 경유).

### 3.2 나가는 소개(센터 → 파트너)
1. 리드 상세 → **파트너에 소개** → 파트너 선택·한 줄 사유·가정 동의 체크.
2. 파트너 포털 "받은 소개"에 아이 이름·학년·보낸 날·사유가 보인다. 전화번호는 보이지 않는다 — 가정이 파트너에게 직접 연락하거나, 원장이 동의 범위 안에서 따로 전달한다(정책 결정 사항, §7).
3. 파트너가 상태를 표시한다: 보냄 → 연락됨 → 등록 / 미등록(+한 줄).
4. 센터 파트너 탭에서 파트너별 등록 수가 잡힌다.

### 3.3 정산(월 1회)
- 파트너 탭에서 월을 고르면 파트너별로 **보내 주신 가정 수·검사 완료·등록 / 저희가 소개한 가정 수·등록**이 나오고, [정산 문구 복사]로 카톡에 붙일 요약이 나온다(숫자와 조건만, 가정 정보 없음).
- 조건(혜택)은 파트너마다 문장으로 적는다 — "검사비 20% 할인", "첫 달 수강료 10% 할인", "소개 1건당 검사 1회 무료" 등. 금전 정산을 자동 계산하지 않는다(v0). 필요해지면 조건을 구조화한다(§8).

## 4. 데이터

| 데이터 | 어디에 | 누가 쓰나 |
|---|---|---|
| 파트너 학원(이름·종류·지역·담당자·전화·상태·조건·자료 링크·메모) | `crm_documents` 의 `partners` 컬렉션 | 원장 |
| 들어온 소개 | 리드 자체 — `leads.channel='파트너'` + `leads.partnerId` | 파트너 포털(만들기)·직원(이후 처리) |
| 나간 소개 | `referrals` 컬렉션(리드 id·파트너 id·사유·동의·상태·파트너 메모) | 직원(만들기)·파트너 포털(상태·메모만)·원장 |
| 파트너 포털 연결 코드·기기 토큰 | `crm_partner_codes`·`crm_partner_tokens` (직원 표와 분리) | 원장(발급·해제) |

개인정보 경계: 전화번호는 `leads.phone`·`partners.phone` 두 칸에만. 포털이 받는 소개 본문·메모에 번호가 있으면 서버가 거부한다. 포털 응답에는 전화·이메일·메모·내부 단계가 없다.

## 6. 어디에 만드나 — 결정

**결정: 세일즈데스크(wb-crm)와 같은 워커·같은 D1 에 두되, 파트너 쪽은 처음부터 경계를 그어 둔다.**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 세일즈데스크 화면 안에 탭 하나 | 가장 빠름 | 외부 사용자(파트너)가 내부 앱 출입구를 쓴다 — 권한 경계가 흐려진다 |
| B. 완전 별도 워커·D1 (`wb-partner`) | 격리 최고 | **리드가 두 곳에 생긴다** — 파트너가 보낸 가정이 센터 리드이기도 해서 두 DB 를 맞추는 동기화(서비스 키·큐)가 필요하고, 전환·정산 수치가 두 곳을 합쳐야 나온다 |
| **C. 같은 워커·D1 + 파트너 전용 출입구·API·표·모듈** (채택) | 리드는 한 곳, 파트너는 자기 문 하나·자기 API 만 본다. 나중에 B 로 떼어낼 때 옮길 것이 정해져 있다 | 워커 하나가 둘 다 서빙 |

C 의 경계:
- 화면: `/partner/`(별도 정적 앱, 세일즈데스크 토큰과 무관한 파트너 토큰)
- API: `/api/partner/*` 만 파트너 토큰을 받는다. 다른 `/api/*` 는 파트너 토큰으로 열리지 않는다.
- 표: `crm_partner_codes`·`crm_partner_tokens`(002 마이그레이션). 문서 컬렉션 `partners`·`referrals`.
- 코드: `crm/partner-api.mjs`(파트너 API 전부) · `crm/partner/`(포털). 세일즈데스크 쪽은 `leads.partnerId`·파트너 탭뿐.

**언제 B 로 떼어내나**(그때 옮길 것: `partner-api.mjs` + `partner/` + `crm_partner_*` 표 + `partners`·`referrals` 컬렉션, 남길 것: `leads.partnerId`):
- 파트너가 10곳을 넘어 파트너마다 직원 계정·자기 학생 명단을 관리해야 할 때
- 파트너에게 센터 리드와 무관한 기능(자기 학원 CRM)을 주게 될 때
- 파트너 트래픽이 센터 직원 앱의 응답을 늦출 때

## 7. 원장이 정해야 하는 것(열린 질문)

1. 나가는 소개에서 **가정 전화번호를 파트너에게 전달하는 방식** — 가정이 파트너에게 직접 연락(기본) / 원장이 동의받고 카톡으로 전달. v0 은 포털에 번호를 싣지 않는다.
2. 파트너별 **혜택 조건의 표준 문구**(검사비 할인률·무료 검사 횟수) — 조건을 구조화(숫자)할지 문장으로 둘지.
3. HubSpot 에서 파트너를 **회사(Company)** 로 만들어 연락처를 연결할지(v0 은 `wb_partner` 문자열만).
4. 포털 안내문·동의 문구(가정에 나가는 문구이므로 원장 확인 필요 — 절대 규칙 7).

## 8. 백로그

- 파트너 포털 Web Push(받은 소개 도착) — 세일즈데스크 쪽 VAPID 와 별도 키.
- 조건 구조화 + 자동 정산표(월별 금액) + 소개 크레딧 원장과의 연결.
- HubSpot Company 매핑, 파트너별 딜 파이프라인 보고서.
- 파트너 안내 QR·소개 링크(가정이 직접 신청하는 공개 폼 — 공개 페이지는 절대 규칙 3 과 함께 따로 설계).
