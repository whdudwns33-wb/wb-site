# WB 학생·보호자 플랫폼 장기 로드맵

## 결론

직원 업무지시서를 그대로 학부모에게 열지 않는다. 화면과 로그인은 `직원`, `보호자`, `학생`으로
분리하고, 현재 D1의 stable `studentId` 정본과 검증된 운영 원장만 함께 쓴다. 이렇게 하면 새 앱을
처음부터 다시 만드는 비용은 줄이면서 직원 메모·연락처·주소가 외부 화면으로 새는 위험을 막을 수 있다.

## 지켜야 할 원칙

1. 이름으로 학생을 추정 연결하지 않고 stable `studentId`만 쓴다.
2. 직원 내부 기록을 그대로 보내지 않고 보호자·학생용 공개 필드만 서버가 다시 만든다.
3. 공개 범위가 넓어질 때마다 동의 버전을 올리고 기존 동의를 자동 승계하지 않는다.
4. 보호자와 학생은 서로 다른 세션·권한을 쓴다. 같은 전화번호만으로 형제를 자동 결합하지 않는다.
5. 발송·출결·차량·회차는 “화면 문구”가 아니라 서버 원장과 revision을 근거로 표시한다.
6. 처음에는 읽기 전용으로 시작하고, 응답이 필요한 기능만 제한된 선택지와 CAS로 연다.

## 단계별 진행

### 1단계 — 오늘 우리 아이

- 오늘 확정 수업, 출결 확인, 수업 5단계 기록 진행
- 오늘 차량의 등·하원 예정시각과 탑승/하차 확인
- 기존 주간 시간표, 보강 응답, 회차 잔여, 공개 피드백
- 내부 메모, 정류장명·주소, 기사/보호자 연락처는 비공개
- 기존 공개 동의 v1은 기존 기능만 유지하고, 위 정보는 공개 동의 v2 후 제공

완료 기준은 다른 학생·내부 메모·주소·전화번호가 응답에 포함되지 않고, 연락처/동의 변경 시 기존
세션이 폐기되는 회귀 테스트를 통과하는 것이다.

### 2단계 — 요청과 알림을 한곳에

- 결석 사유 선택과 보강 제안 수락/재조율
- 횟수제 잔여 3·1·0회 안내
- 차량 탑승/하차 알림의 접수·불명 상태 표시
- 교재 주문→학원 도착→학생 인계의 단계 구분
- 학부모 요청은 자유 채팅보다 `상담 요청`, `일정 확인`, `정보 수정 요청` 같은 정형 항목부터 제공

### 3단계 — 학생 학습 앱

- 오늘 숙제와 온라인 프로그램 바로가기
- 메타수학 학생홈과 클래스카드는 승인된 공식 HTTPS 주소만 새 창으로 열기
- 외부 학습 링크는 학생 공개 동의 v2에서만 제공하고 기존 v1 연결에는 자동 추가하지 않기
- 외부 아이디·비밀번호·쿠키·학습 결과는 WB가 받거나 저장하지 않으며 iframe·스크래핑·자동 로그인을 사용하지 않기
- 교재·진도·단어시험 범위
- 학생이 하는 자기 체크와 선생님이 확정하는 수행 기록 분리
- 주간 목표와 누적 성취, 작은 보상 배지
- 초등 저학년은 그림/한 문장 중심, 중·고등은 목표·오답·시간 관리 중심 화면

학생 앱에는 학부모 연락처, 상담 기록, 교사 평가 원문을 넣지 않는다.

### 4단계 — 가족 계정과 다자녀

- 보호자와 학생 사이에 명시적인 학생별 grant를 저장
- 두 자녀를 한 화면에서 전환하되 자녀별 동의·초대·해지를 독립 관리
- 분실 기기 전체 로그아웃, 활성 기기 목록, 유휴 세션 만료
- 보호자 변경·가족관계 변경 시 이전 보호자 세션 즉시 폐기

### 5단계 — 운영·학습 분석

- 원장: 미완료 수업 기록, 보강 지연, 차량 미하차, 교재 미인계 예외만 모아 보기
- 선생님: 담당 학생별 다음 행동과 최근 변화
- 보호자: 출석률·숙제 추세·월간 성장 요약(진단이나 순위로 과장하지 않음)
- 학생: 자신의 목표 대비 진행률
- 알림 과다를 막는 주간 묶음 보고와 조용한 시간 설정

## 아카플로우 강사 5명 제한 대응

아카플로우 담당 강사를 WB의 실제 담당 교사 정본으로 사용하지 않는다. WB에는 모든 실제 교사를
stable staff ID로 유지하고, 아카플로우의 5개 강사 계정은 외부 입력용 그룹 또는 대표 계정으로만
매핑한다.

- 학생 연결 정본: WB `studentId`
- 실제 담당 정본: WB `teacherIds`
- 아카플로우 강사: `externalTeacherId` 보조값
- 담당 불일치: 자동 덮어쓰기 금지, 관리자 매핑 검토함으로 보냄
- 연락처 가져오기/내보내기: 이름만으로 저장하지 않고 stable 학생 연결을 확인한 뒤 적용

API가 생기지 않아도 CSV/XLSX 가져오기와 승인된 브라우저 보조 작업을 같은 검토함에 넣으면 된다.
브라우저 자동화 결과도 바로 정본으로 쓰지 않고 `수집 → 차이 확인 → 승인 → 저장` 순서를 유지한다.

## 서로 다른 다섯 가지 활용 관점

1. **운영 관점**: 원장은 예외만 보고, 선생님은 다음 행동만 본다.
2. **보호자 신뢰 관점**: “보냈다”가 아니라 출결·차량·교재의 확인 근거와 시각을 보여준다.
3. **학습 관점**: 수업 기록을 숙제·오답·다음 목표로 이어 학생의 자기관리 루프를 만든다.
4. **서비스 관점**: 월제와 횟수제를 분명히 구분하고 잔여 회차·보강·교재 상태 문의를 줄인다.
5. **위험 관리 관점**: 미하차, 결석 후 보강 미정, 수업 기록 누락, 연락처 재동의를 먼저 경고한다.

## 다음 우선순위

1. 출근 후 보호자·학생 앱을 실제 휴대폰과 태블릿에서 연결·해제까지 검증
2. 학생 공개 동의 v2와 공식 외부 학습 링크를 D1 → 두 Worker → 학생/직원 화면 순서로 배포
3. 내부 직원 2명과 실제 발송 없는 보호자·학생 테스트 계정으로 일주일 파일럿
4. 문의가 가장 많은 항목을 기록해 다음 기능 하나만 선택

성공 지표는 화면 수가 아니라 `학부모 반복 문의 감소`, `수업 기록 당일 완료율`, `보강 확정 소요시간`,
`차량 미하차 확인시간`, `잘못 연결된 학생 0건`으로 본다.
