## 1. 처음 시작

1. 주소를 연다 → **관리자 비밀번호 만들기**(8자 이상). 처음 한 번만.
2. **관리** 탭 → 직원 등록 → **링크 발급** → 1:1 로 보낸다(7일 안에 한 번 열면 그 기기에 연결).
3. **허브스팟** 탭(원장) → 연결 상태 확인. 토큰이 없으면 §5 대로 등록한다. 기존 고객이 있으면 §4의 백업·센터앱/큐 대조 후 파이프라인 매핑·속성 생성·첫 가져오기를 진행한다. 자동 동기화는 기본 꺼짐이며 별도로 켠다.
4. **파트너** 탭(원장) → 파트너 학원 등록 → [링크 발급] → 파트너 원장에게 보낸다.
5. 오늘부터: **＋ 새 문의**에 카톡·전화 메모를 그대로 붙여 넣으면 유입 채널과 핫 리드 여부가 자동으로 표시된다.

## 4. HubSpot 연동 — 어떻게 도나

**학원 등록 단계(2026-10-16 원장 결정)**: 실제 HubSpot의 문의 → 레벨테스트·체험 → 등록 결정 대기 → 등록(성사)/미등록을 정본으로 사용한다. 로컬 키는 `inquiry/trial/trial_review/won/lost`이며 HubSpot 파이프라인 자체는 바꾸지 않는다. 재원·이탈위험·이탈 등 등록 후 관리는 기존 `academyStatus`(`wb_academy_status`)에 따로 기록한다. 기존 `active/at_risk/churned` 리드는 단계·판정·날짜를 보존하고 화면의 이전 상태 확인 영역에 표시한다. 새 영업 단계는 담당자가 확인해서 선택하며, 가져오기가 과거 기록을 임의로 등록 성공으로 바꾸지 않는다. 해당 옛 단계의 전송은 `LEGACY_STAGE`로 보류하며, 기존 실패 전송 취소는 원본 확인 절차를 따른다. 일괄 데이터 변경이나 승인 대기 자동 승인은 하지 않는다.

- **원본 경계**: 센터앱에 연결한 고객의 예약·참여·혜택·센터 CS와 예약별 HubSpot 딜은 센터앱이 관리한다(§11). 그 외 기존 CRM 리드는 연락처·딜을 HubSpot과 연동하고 팔로업·기록·판정·KPI를 세일즈데스크에 둔다. 기존 CRM 모델은 리드마다 연락처 하나, 파이프라인마다 딜 하나(`hubspot.deals.inspection / academy`)이며 센터앱의 예약별 딜을 임의로 여기에 넣지 않는다.
- **반영 큐**(원장 CRM 규칙 P4-A/B): 리드가 바뀌면 서버가 `contact`(연락처 속성) 줄을, 단계가 바뀌면 `deal`(딜 단계) 줄을, 기록이 생기면 `note`(노트) 줄을 만든다. 같은 리드의 같은 종류는 한 줄로 합쳐진다.
  **수동 모드**에서는 빠른 입력 자동 승인 설정을 쓰고 기존 딜 단계 전이는 원장이 승인한다. 승인한 검토 줄의 단계가 다시 바뀌면 승인 대기로 돌아간다. **자동 모드**에서는 이후 새 연락처·딜·노트 줄을 자동 승인하지만, 켜기 전에 남은 승인 대기 줄은 자동 승인하지 않는다(그 줄에 새 변경이 합쳐져도 대기를 유지). 리드가 다른 파이프라인으로 옮겨지면 옛 파이프라인의 열린 딜 줄은 반려된다. 승인된 줄은 [지금 반영] 또는 크론이 보내며, 먼저 생긴 승인 대기·실패가 있으면 같은 고객의 뒤 작업도 기다린다.
- **검사 여정 → 학원 등록**으로 넘기면 검사 여정 딜은 성사로 닫히고 학원 등록 딜이 트라이얼로 생긴다(큐 두 줄).
- **가져오기**: `lastmodifieddate` 기준 변경분 연락처(+연결된 딜)를 리드로 읽는다. 기존 연락처 연결표·`wb_crm_lead_id`로 연결하며, 새 리드는 `hs_<연락처 ID>`를 쓴다. 우리 쪽 승인 대기·반영 대기·실패 큐가 있으면 덮지 않고 **다음 가져오기 때 ID로 다시 읽는다**(커서와 별도). 원장이 지운 리드는 되살리지 않고, 이름에 전화 패턴이 섞인 연락처는 들여오지 않는다. 기록·팔로업·메모는 건드리지 않는다.
- **중복 방지**: 연락처를 만들기 전에 이메일(첫 그룹)·전화(계산 속성 `hs_searchable_calculated_*` 숫자 + 우리 표기)로 찾는다. 같은 연락처가 이미 다른 리드에 연결돼 있으면 가로채지 않고 큐에 `LINKED` 실패로 남긴다(원장이 두 리드를 합치거나 전화를 바꾼다).
- **속성**: 표준(이름·전화·이메일·lifecyclestage=customer 는 성사 때만) + WB 사용자 속성 `wb_source_channel`(선택지에 `파트너` 보강)·`wb_academy_status`·`wb_credit_balance`·`wb_referrer_contact_id`·`wb_retest_due_date`·`wb_inspection_type`·`wb_inspection_date`·`wb_child_name`·`wb_child_birth`·`wb_child_grade`·`wb_consult_date`·`wb_lost_reason`·`wb_crm_lead_id`·`wb_partner`. 포털에 없는 속성은 만들기 전까지 보내지 않는다.
- **단계 매핑**: 우리 단계 라벨 = HubSpot 딜 단계 라벨이면 자동(검사 여정·학원 등록). `성사(등록)`↔`성사된 거래`, `미성사`↔`성사되지 않은 거래` 는 별칭. 안 맞는 단계는 손으로 고른다.

**자동 동기화의 범위와 주기**: 기본은 꺼짐이다. 켜면 Worker가 15분마다 변경분 가져오기 → 승인된 큐 최대 2건 전송 순서로 실행한다. 한 번의 연락처 검색은 1페이지(최대 10건)이며 남은 페이지는 다음 실행에서 이어간다. 연락처 기본정보·매핑된 영업 단계를 양방향으로 연결하고, 상담 기록은 세일즈데스크 → HubSpot 노트 방향만 지원한다. 센터앱 연결 고객, 삭제 전파, 관계관리 기록, 검사 점수, HubSpot에서 작성한 노트의 역수입은 대상이 아니다. 자동 동기화를 꺼도 **기존 승인 큐의 15분 자동 전송은 유지**된다. 화면의 60초 새로고침은 로컬 데이터 조회이며 동기화 실행 주기가 아니다. 핵심 연동은 공식 API와 기존 Worker가 맡으며 n8n은 필수가 아니다.

**전체 보정**: 수동 [전체 가져오기]와 자동 보정은 검색 API 대신 연락처 기본 목록 API의 객체 커서를 사용한다. 한 번에 최대 25개씩 읽고 `fullRun`·`after`를 보존해 다음 실행에서 이어간다. 마지막 전체 보정 완료(`lastFullAt`) 뒤 24시간이 지나고 진행 중인 페이지가 없으면 자동 보정을 다시 시작한다. 검색 인덱스가 늦게 반영한 신규 연락처나 아직 연결되지 않은 고객도 이 전체 보정으로 다시 확인한다. 연락처가 많으면 완료까지 여러 주기가 필요하므로 "24시간마다 전체 완료"를 뜻하지 않는다. 처음 전체 가져오기에는 검색 API의 10,000건 한도를 적용하지 않는다.

**원장 활성화 순서**:

1. **관리 → 전체 백업(JSON)**을 저장소 밖에 보관한다. 센터앱 연결 고객과 기존 HubSpot 연락처·딜을 대조하고, 승인 대기·실패 큐를 원본과 함께 검토한다. 자동 모드를 켜서 예전 대기 건을 일괄 승인하지 않는다.
2. [다시 확인] → [HubSpot 파이프라인 불러오기] → 매핑 확인 → [매핑 저장] → [없는 속성 만들기]. 자동화 활성화에는 토큰·연결 사용 설정과 **두 로컬 파이프라인의 모든 단계가 실제 HubSpot 단계에 빠짐없이 매핑**되어야 한다. 두 파이프라인을 같은 원격 파이프라인으로, 한 파이프라인의 여러 단계를 같은 원격 단계로 겹쳐 매핑할 수 없다.
3. 기존 큐를 정리한 뒤 [전체 가져오기]를 실행하고 [변경분 가져오기]로 `more`가 없어질 때까지 이어간다. `created/updated/conflicts/invalid/retry/portalSkipped` 결과를 확인한다. 이 과정에서 기존 연결의 원격 비교 기준을 저장한다. `REMOTE_BASELINE`은 기준이 없는 기존 고객이므로, 원본/큐 확인 후 가져오기를 먼저 한다.
4. [자동 동기화 켜기] → 서버가 **켜짐**을 확인한 뒤 [지금 동기화]. 마지막 실행·완료 시각과 가져오기/보내기 결과, 실패·충돌을 확인한다. 실행 중인 작업이 있으면 중복 실행을 거절한다. 운영 활성화 여부는 배포 여부와 별도로 확인한다.

**충돌·불확정 결과**: 앱 저장은 편집 시작 버전으로 검사한다. 충돌 시 서버 최신값을 표시하고 내 초안을 메모리에 보관한다. [내 입력 검토]에서 변경한 항목만 비교해 재저장하거나 최신 내용을 선택한다. 새로고침/로그아웃 전에 해결해야 하며 삭제된 고객은 초안으로 복원하지 않는다. 자동 전송은 원격 연락처·딜을 다시 읽어 이전 비교 기준과 다르면 `REMOTE_CONFLICT`로 보류한다. 통신 중단 등으로 실제 외부 반영 여부가 불명확하면 `UNCERTAIN`으로 남기고 자동 재생성·[다시 시도]를 막는다. **HubSpot 원본을 먼저 확인**한 뒤 불필요해진 전송만 [이 전송 취소]로 반려한다(확인한 실패 취소는 `reviewed:true`). 반려 후에는 가져오기가 HubSpot 값을 적용할 수 있다. 호출 한도·인증 오류는 승인 큐에 남아 다음 주기에 다시 확인한다.

**현재 한계**: 연락처 수정시각이 변하지 않는 딜 변경은 이미 연결된 연락처를 실행당 최대 20개씩 순환 조회해 발견한다. 연결 수가 많으면 한 바퀴에 여러 주기가 걸리며, 아직 연결되지 않은 연락처는 전체 보정을 기다릴 수 있다. 변경분 검색은 5분을 겹쳐 읽지만 그보다 긴 인덱스 지연은 즉시 발견을 보장하지 않고 전체 보정으로 보완한다. **변경분 검색**의 시간창 결과가 10,000건을 넘으면 `SEARCH_LIMIT`으로 멈추며 자동 시간창 분할은 아직 없다. 이 경우 원본 대조 후 [전체 가져오기]로 기본 목록 보정을 시작할 수 있다. 주기·페이지·실행 시간 제한 때문에 실시간 반영이나 모든 필드의 완전 복제를 보장하지 않는다.

충돌·검증 실패의 연락처 재조회도 실행당 최대 10개를 순환한다. 전체 가져오기 진행 중에는 목록 페이지가 연락처와 딜을 함께 읽으므로 연결 재조회·재시도 묶음을 중복 실행하지 않는다. 기존 재시도 목록과 연결 순환 위치는 보존하고 전체 완료 후 변경분 실행에서 재개한다. 전체 목록 25개·변경분 검색 10개·연결 재조회 20개·재시도 10개·크론 전송 2건은 D1 왕복 지연과 90초 실행 제한을 고려한 배치이며, 같은 연락처가 겹치거나 오류/시간 제한이 있으면 실제 처리 수는 더 적다. 고객별 잠금·버전 검증을 유지하며 가져온 고객을 최대 3명씩 병렬 저장한다. 한 묶음이 실패하면 진행 중인 저장을 모두 마친 뒤 다음 묶음을 중단한다. 제한 전에 저장한 고객은 유지하고 실패한 페이지 커서는 그대로 두므로 다음 실행에서 중복 생성 없이 다시 확인한다. 수동 [지금 반영]의 최대 25건과 자동 주기의 최대 2건을 혼동하지 않는다.

## 5. HubSpot 토큰 등록 (원장 1회)

1. HubSpot → 설정 → 통합 → **비공개 앱(Private Apps)** → 앱 만들기. 스코프: `crm.objects.contacts`(읽기·쓰기) · `crm.objects.deals`(읽기·쓰기) · `crm.schemas.contacts`(읽기·쓰기 — 속성 만들기) · `crm.objects.owners`(읽기). 노트는 contacts 쓰기 스코프로 충분하다.
2. 토큰을 GitHub 저장소 **Settings → Secrets and variables → Actions** 에 `HUBSPOT_ACCESS_TOKEN` 으로 저장한다.
3. Actions → **Deploy wb-crm worker** → Run workflow. 워크플로우가 저장소 시크릿을 워커 시크릿으로 복사한다(값은 마스킹, 로그에 안 남음). 이후 main 배포마다 같은 단계가 돌아 토큰을 갈아 끼워도 된다.
4. 허브스팟 탭 → [다시 확인] → "연결됨".

토큰은 저장소·화면·응답·로그 어디에도 적지 않는다(절대 규칙 5). 손으로 넣을 때: `printf '%s' "$TOKEN" | npx wrangler secret put HUBSPOT_ACCESS_TOKEN` (`crm/` 에서).

## 6. 서버 API 요약 (`/api/*`, JSON, 모든 응답 `Cache-Control: no-store`)

| 경로 | 누가 | 하는 일 |
|---|---|---|
| `GET /api/health` | 누구나 | `{ok, app:'wb-crm', setup, hubspot(토큰 유무), now}` |
| `POST /api/setup` · `/api/login` · `/api/password` · `/api/link-exchange` · `GET /api/me` · `POST /api/logout` | — | desk 와 같은 인증(원장 PBKDF2 비밀번호, 직원 1회용 링크, Bearer 토큰 sha256 저장, 원장 30일·직원 180일) |
| `GET /api/staff` · `POST /api/staff {op}` | 원장 | 직원·링크 관리 |
| `GET /api/docs?since=` · `POST /api/docs {changes}` | 인증 | 문서 읽기·쓰기(컬렉션 규칙은 `crm-api.mjs` RULES). 쓰면 반영 큐가 생긴다(`queued`) |
| `GET /api/hubspot/queue?status=&leadId=` · `POST /api/hubspot/queue {op:approve\|reject\|retry\|unapprove\|approveAll, ids, reviewed?}` | 읽기 인증·쓰기 원장 | 실패 취소는 `reviewed:true` 필요. `UNCERTAIN` 재시도 차단 |
| `GET /api/hubspot/status` · `/pipelines` · `GET\|POST /properties` · `POST /pull {full}` · `POST /push {limit}` | 원장 | 연결·파이프라인 제안·속성 점검/생성·가져오기·반영. status에 `automation` 포함 |
| `POST /api/hubspot/sync {enabled:boolean}` 또는 `{run:true}` | 원장 | 자동화 켜기/끄기 또는 지금 실행. `{ok, automation:{enabled,intervalMinutes,lastRunAt,lastSuccessAt,lastResult,error,running}}` 반환 |
| `POST /api/partners {op:link\|revoke\|devices, partnerId}` | 원장 | 파트너 포털 링크·기기 |
| `POST /api/partner/link-exchange` · `GET /api/partner/me` · `GET\|POST /api/partner/referrals` · `POST /api/partner/referrals/<id>/status` · `POST /api/partner/logout` | 파트너 토큰 | 포털(`partner-api.mjs`). 파트너 토큰으로는 다른 `/api/*` 가 열리지 않고, 직원 토큰으로는 `/api/partner/*` 가 열리지 않는다 |
| `GET /api/export` | 원장 | 전체 백업 JSON(토큰 없음) |

동기화 실행 결과를 정상적으로 반환하면 일부 보류가 있어도 `ok:true`이며 실제 처리 상태는 `automation.error`와 `lastResult`로 판단한다. 보류·실패가 있으면 이전 `lastSuccessAt`을 유지한다. 인증·입력·활성화 조건 거절은 별도 오류 응답이다.

## 7. 배포 — 원장은 머지만

`.github/workflows/deploy-crm.yml` 이 main 에 `crm/` 변경이 올라오면 돈다: 테스트 → `node crm/build.mjs` → D1 `wb-crm` 을 이름으로 찾고 없으면 생성 → `migrations/*.sql` 전부 순서대로(**전부 `IF NOT EXISTS`**) → 번들 dry-run(node: 모듈 금지) → 배포 → `HUBSPOT_ACCESS_TOKEN` 저장소 시크릿이 있으면 워커 시크릿으로 복사 → `/api/health`.
필요한 저장소 시크릿: `CLOUDFLARE_API_TOKEN`(D1 편집 + Workers 편집)·`CLOUDFLARE_ACCOUNT_ID`, 선택 `HUBSPOT_ACCESS_TOKEN`·`WB_SALESDESK_READ_KEY`(센터앱 전용 읽기 키). 후자의 같은 키는 센터앱 서버에만 설정한다. 기존 학습 앱 연결 키·HubSpot 토큰을 재사용하거나 교체하지 않는다.

자동 동기화 배치는 **Workers Paid 환경**을 전제로 한다. 2026-10-16 운영 Worker의 비밀값을 제외한 설정 조회에서 `usage_model:standard`를 확인했으며, Standard는 [Workers Paid 사용 모델](https://developers.cloudflare.com/workers/platform/pricing/#workers)이다. [D1의 실행당 쿼리 한도](https://developers.cloudflare.com/d1/platform/limits/)는 Paid 1,000회, Free 50회다. Free 환경은 현재 동기화 배치의 지원 대상이 아니며, 옮기려면 배치를 더 잘게 나누는 별도 검증이 필요하다. 이 확인은 요금제 변경·결제 실행을 뜻하지 않는다.

## 8. 로컬 실행·테스트

```
node scripts/check.mjs --only crm                     # crm 테스트 전부(순수 로직·HubSpot 클라이언트·서버·파트너)
node crm/crm-core.test.cjs && node crm/hubspot.test.mjs && node crm/crm-api.test.mjs
PORT=8892 node crm/dev-server.mjs                     # 로컬 서버 (D1 대역: crm/.local/crm.sqlite — 커밋 금지). HUBSPOT_ACCESS_TOKEN=… 로 실제 연동 시험
node crm/build.mjs                                    # dist 조립 (배포 워크플로우가 하는 일과 같다)
```

자동 동기화 검사는 `crm-api.test.mjs`(가짜 HubSpot·D1에서 권한/활성화·선점·CAS·원격 충돌·결과 미확정·증분/전체 커서·24시간 보정), `hubspot.test.mjs`(공식 API 요청·변경 필드 변환·기본 목록 페이지), `app-sync.test.cjs`(실제 앱의 상태 표시·서버 확인·초안 복구·삭제 보호·실패 취소)를 사용한다. 가상 데이터 검사 통과와 운영 자동화 활성화 확인은 별개다.

## 10. 친구맺기·서포터즈·맘스쿨

근거는 통합데스크의 승인 매뉴얼(2026-09-16 운영 기준, 같은 항목은 2026-09-28 부모앱 안내 우선)과 2026-10-06 원장 설명이다.

- **친구맺기**: 월 1회 리뷰를 부모앱에 링크 또는 캡처로 등록한다. 기본 무료 활동지·3개월 후 소검사 1회와, 첫 리뷰 후 이용하는 청크브레인·어휘브레인·브레인레터를 구분한다. 소검사 완료는 회원 탈퇴가 아니다.
- **서포터즈**: 등록일부터 자료·비문학 독서 앱 혜택. 매달 후기·지인 소개·브런치 동반 중 1회 이상을 확인하며 한 달에 몰아서 다른 달을 충족하지 않는다. 3개월간 월별 활동 확인 후 소검사를 반복 제공한다. 미활동은 안내·보완을 거쳐 담당자가 판단하며 자동 종료하지 않는다. 활동 인정과 소개 포인트 지급은 별개다.
- **맘스쿨**: 검사를 마친 보호자 4~6명이 주제별로 차를 마시며 이야기하는 관계 형성 소모임이다. 주제·일시·장소·진행 담당자·참석 상태·대화 요약·다음 연락을 기록한다. 정원은 확정·참석 인원을 기준으로 하며, 실제 결석으로 4명 미만이 된 참석 기록도 남길 수 있다. 형제별 고객 기록은 같은 보호자 한 명을 대표하는 기록 하나로 선택한다. 참석이 서포터즈 활동 인정·가입·매출·딜 전환으로 자동 처리되지는 않는다.

센터 부모앱의 리뷰 증빙·혜택 이용권·서포터즈 원장이 이미 존재한다. 관계관리 기록은 **직원이 남기는 영업 후속 업무**이며 이용권을 발급하거나 원본을 변경하지 않는다. §11의 센터앱 조회 요약은 고객 상세에 별도로 표시하고 이 네 컬렉션을 덮어쓰지 않는다. 이 네 컬렉션은 HubSpot 연락처·딜·노트 반영 대상에도 포함되지 않는다.

저장은 기존 D1 문서 표의 `memberships`, `programActivities`, `programExams`, `gatherings`를 사용한다. 원장·직원이 사용하고 파트너 포털에 공개하지 않는다. 새 기록은 서버 응답을 확인한 뒤 완료 처리하며, 충돌·검증 실패 시 입력을 남긴다. 소검사의 정확한 기준일·예약·완료일을 따로 기록하고 이전 회차 완료일을 지우지 않는다. 프로그램 전환·중복 혜택·포인트 금액·자동 제한 정책은 추정해서 추가하지 않는다.

## 11. 센터앱 고객 연결

고객 상세 → **센터앱 원본 → 고객번호 연결**에서 같은 아이의 센터앱 `/admin/family/<번호>`를 확인해 연결한다. 센터앱 `family.id`는 아동별 고객번호다. 같은 보호자의 형제를 전화번호로 합치지 않는다. 하나의 번호는 CRM 고객 하나에만 연결할 수 있다. 연결 변경은 원장만 하며 직원은 상태를 조회한다.

고객 화면을 열면 저장 요약을 보여 준 뒤 최신 상태를 조회한다. **센터앱 최신 상태 확인**으로 다시 조회할 수도 있다. 친구맺기·서포터즈·설치 확인·부모앱 이용 기간·학습 앱 이용 조건·미완료 CS/다음 연락일·브런치 참석 횟수, 기존 HubSpot 연락처/예약별 딜 번호만 읽는다. 이름·전화·점수·문진·후기 원문·로그인 초대코드는 가져오지 않는다. 브런치를 맘스쿨 기록과 자동 병합하지 않고 학습 앱 이용 조건 충족을 외부 계정 준비 완료로 표시하지 않는다.

서버는 고정 센터앱 주소의 `GET /api/integrations/salesdesk/families/<번호>`를 전용 키로 호출한다. 브라우저에는 키가 전달되지 않는다. 오류·키 미설정은 현재 상태 미확인으로 표시하며 이전 요약과 확인 시각을 유지한다. 연결 번호가 바뀌면 이전 아이의 요약은 비운다. 새 D1 표 `crm_portal_links`의 버전·유일 제약으로 동시 연결과 중복을 막고 전체 백업에도 포함한다.

**HubSpot 중복 쓰기 보호**: 연결한 CRM 고객은 연락처·딜·노트 전송을 보류한다. 기존 큐는 삭제하지 않고 실행 시 `PORTAL_LINKED`로 남는다. 조회된 원본에 연결된 연락처·딜과 겹치는 전송도 차단한다. 가져오기는 연결 고객 및 조회된 원본 연락처를 `portalSkipped`로 건너뛴다. 아직 연결·조회하지 않은 고객까지 자동 판별하지는 못하므로 전체 가져오기/전송 확대 전에 기존 연결을 대조한다. 진행 중인 반영과 고객번호 연결은 함께 실행하지 않으며, 외부 요청 시간 초과의 실제 반영 여부는 별도로 확인해야 한다.

검증: `node scripts/check.mjs --only crm`. `app-portal.test.cjs`는 입력 보존·조회 실패·동시 변경·세션 종료를, `crm-api.test.mjs`는 인증·형제 구분·원본 필드 제한·오류 보존·HubSpot 전송 보호를 가상 데이터로 확인한다.
