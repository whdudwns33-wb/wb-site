이 문서는 **"지금 어디까지 돼 있고, 다음에 무엇을 하며, 고칠 때 어디가 깨지는가"** 만 적는다. 무엇을 하는 앱인지·화면·API 는 `crm/README.md`,
파트너 연계의 기획·구조 결정은 `docs/파트너학원-연계-기획서-v0.md`, 저장소 공통 규칙은 루트 `AGENTS.md`(= `CLAUDE.md`).

## 0. 시작하기 전에 돌릴 것

```
node scripts/check.mjs --only crm        # crm 하위의 순수 로직·API·화면 검사 전부
node scripts/check.mjs                   # 저장소 전체 — PR 전 필수(초록 아니면 올리지 않는다)
PORT=8892 node crm/dev-server.mjs        # http://127.0.0.1:8892 (빌드 없이 app/ 그대로), 포털은 /partner/
node crm/build.mjs                       # dist/ 조립(배포 워크플로우와 같은 일) — dist/·.local/ 은 커밋 금지
```

HubSpot 실제 연동을 로컬에서 시험하려면 `HUBSPOT_ACCESS_TOKEN=… PORT=8892 node crm/dev-server.mjs` 처럼 **환경변수로만** 넘긴다. 파일·저장소·로그에 두지 않는다.

## 1. 지금 상태 (2026-10-16)

- **학원 등록을 HubSpot 기준으로 맞추기로 원장 결정**: 운영 원장 로그인 후 실제 학원 파이프라인이 문의·레벨테스트/체험·등록 결정 대기·등록·미등록 5단계임을 확인했다. 앱도 이 영업 단계로 맞추고 재원·이탈위험·이탈은 `academyStatus`로 구분한다. 기존 옛 단계의 리드·판정·날짜·대기 큐는 보존하고 자동 등록 성공 전환을 하지 않는다. UI는 옛 단계 고객을 별도 확인 영역에 표시한다. 가져오기 결과에 검증 실패·재시도 대기·센터앱 관리 건수를 함께 표시한다. 운영 반영 및 자동 동기화 활성화는 아래 절차로 따로 확인한다.

- **자동 양방향 동기화 구현·검증 완료(PR #470), 운영 활성화 대기**: 원장 요청에 따라 기존 공식 API·Worker를 확장했다. 기본 꺼짐이며 원장이 전체 단계의 유효·유일 매핑을 확인해 켜면 15분마다 변경분 가져오기 → 승인된 큐 최대 5건 전송을 수행한다. 이후 새 연락처·영업 단계·노트 줄은 자동 승인하지만 기존 승인 대기는 그대로다. 끄면 기존 승인 큐 크론만 유지한다. 센터앱 연결 고객·삭제 전파·관계관리·검사 점수는 제외하며 노트는 앱→HubSpot만 지원한다. 운영 전 백업·센터앱/큐 원본 대조·첫 가져오기·활성화 순서는 README §4.
  전역/고객별 작업 선점·문서/큐 버전 검사·원격 비교 기준·실패 큐 보호를 추가했다. 리드 편집 충돌은 최신 서버값과 초안을 보존하고 항목 비교 후 재저장한다. 결과 미확정은 `UNCERTAIN`으로 재시도를 막으며 실패 전송 취소에는 원본 확인이 필요하다. 상태 API와 원장 화면에 켜짐·진행·마지막 실행/완료·결과·오류를 표시한다. CRM 9/9 파일(API 34·HubSpot 13·동기화 UI 25개 검사 포함)을 통과했다. 전체 검사 315/315·자산 조립·Worker dry-run·PC/모바일 가상 화면 검증을 통과했다. 독립 리뷰의 최대 배치(가져오기 55건·전송 5건)는 D1 740쿼리였다. ## 3. 고칠 때 깨지는 자리

- **센터앱 연결**: `portal-api.mjs`는 고정 원본·전용 서버 키·응답 허용 목록을 유지한다. `crm_portal_links` 번호/버전은 일반 `/api/docs`로 쓰지 않는다. 실패한 원본 조회를 빈 정상 값으로 바꾸지 않는다. `crm_hs_inflight`는 진행 중 HubSpot 작업과 연결 변경의 경합을 막는다. `enqueueFor`, `ensureContact`, 딜 처리, push/pull의 연결 보호를 함께 확인한다. 운영 포털 위치는 이전 C: 폴더/5000 포트와 다를 수 있으므로 배포 전 실제 프로세스를 확인한다.

- **`crm-core.js` 하나를 브라우저(app.js·partner.js 는 서버 응답만 씀)와 서버(crm-api·crm-shared·partner-api·hubspot.mjs)가 같이 읽는다.** 상수·검증 함수를 바꾸면 `node scripts/check.mjs --only crm` 전체를 돌린다. IIFE + `module.exports` 가드 형식을 지킨다(워커 번들은 esbuild 가 CJS 로 알아서 잇는다).
- **자동 동기화·저장 충돌**: `runHubspotSync`가 자동 모드의 가져오기→보내기와 수동 모드의 승인 큐 전송을 나눈다. 수동 pull/push/설정도 같은 전역 선점을 사용하고 고객 저장은 고객별 선점·CAS를 지킨다. `autoSync`는 `/api/hubspot/sync`에서만 켜며 일반 settings 저장으로 덮지 않는다. outbox의 최초 편집 버전·기준 원본, 성공 응답 뒤 후속 편집 버전 진전, 실패/미확정 큐 차단을 함께 유지한다. 원격 비교 기준을 단순히 최신값으로 덮어 충돌 검사를 우회하지 않는다. 충돌 초안은 기기 메모리뿐이며 새로고침/로그아웃 경고와 항목 재검토를 보존한다.
- **전체/변경분 커서**: 전체 보정은 기본 목록 GET의 객체 커서, 변경분은 검색 시간창 커서다. `fullRun`을 페이지 사이에 유지하고 전체 끝에서만 `lastFullAt`을 기록한다. 두 커서를 섞거나 매 페이지 전체 보정을 재시작하지 않는다. `/api/hubspot/sync`가 결과를 정상 반환한 `ok:true`만으로 모두 성공으로 판단하지 말고 `automation.error`·`lastResult`·`lastSuccessAt`을 본다.
- **관계관리 저장**: `memberships`·`programActivities`·`programExams`·`gatherings`는 `expectedUpdatedAt` 숫자가 필수다(새 기록 0). D1 문장 안에서 버전·참조 원본·친구맺기 소검사 1회 한도를 함께 검사한다. 화면은 `saveRelationship`의 직접 저장·재조회 경로이며 기존 낙관적 큐로 바꾸지 않는다. ID는 PII 본문 검사 대상이 아니지만 참가자 메모·다음 행동은 검사한다. 관계 기록은 삭제하지 않고 상태를 바꾼다.
- **채널 목록 `CHANNELS`** 는 HubSpot `wb_source_channel` 선택지와 1:1 이다. 값을 더하면 `hubspot.mjs` `WB_PROPERTIES` 를 통해 [없는 속성 만들기]가 PATCH 로 선택지를 보강한다(기존 선택지·hidden 은 보존). 값을 빼거나 이름을 바꾸면 기존 리드·HubSpot 양쪽이 어긋난다.
- **단계 키**(`STAGES`·`STAGE_LABEL`·`STAGE_ALIASES`)를 바꾸면 저장된 매핑(`settings.hubspot.map[pipeline].stageMap`)과 리드의 `stage` 가 어긋난다. 라벨만 바꾸는 것은 안전하지만 자동 매핑은 HubSpot 단계 라벨과의 일치로 돈다.
  학원 등록의 현재 영업 단계는 5개이며 표시에는 `stageLabel(pipeline,stage)`를 쓴다. 이전 `active/at_risk/churned`는 기존 리드 보존용으로만 허용하고 새 선택지·역매핑에서 제외한다. `academyStatusOf`로 등록 후 상태를 읽으며, 기존 값을 보강하는 것만으로 전송 큐를 만들지 않는다. 옛 단계 전송은 `LEGACY_STAGE`로 차단한다. 영업 단계 확인 전에는 보류/해제도 실행하지 않는다. 센터앱 소유의 정상 대기는 `push.portalHeld`로 구분하지만 실패·결과 미확정은 계속 확인 대상으로 남긴다.
- **반영 큐 규칙은 `crm-shared.mjs` `enqueueFor` 한 곳**: 종류별 한 줄(딜은 파이프라인별), 수동 모드에서 승인된 검토 줄의 단계가 바뀌면 `pending`. 자동 모드 새 줄은 승인하지만 기존 pending 병합은 pending을 유지한다. 다른 파이프라인의 열린 딜 줄은 반려, 새 줄의 `created_at`은 그 리드의 기존 줄보다 크게(`tick`), 큐 UPDATE 버전은 이전보다 커야 한다. 먼저 생긴 pending/failed가 같은 고객의 뒤 전송을 막는다. 작업 선점 시 `UNCERTAIN`으로 표시하므로 워커 중단 뒤 자동 재생성하지 않는다. 실패 취소의 원본 확인과 `reviewed:true`를 제거하지 않는다.
- **PII 규칙 정본은 `crm-core.js`**(`PII_PATTERNS`·`findPii`). 서버는 `LEAD_PII_SKIP`(phone·email·hubspot·creditBalanceHs)을 건너뛴다. 새 id 필드를 리드에 더하면 숫자열이 오탐될 수 있다 — skip 에 넣거나 영문이 섞인 슬러그를 쓴다. 화면도 저장 전에 같은 검사로 막는다(막지 않으면 거절된 저장이 "리드가 사라진 것"처럼 보인다).
- **서버가 가진 필드**: `leads.hubspot`·`creditBalanceHs` 는 클라이언트 값을 버리고 이전 값을 잇는다(`ruleLeads`). push 는 `patchDocFields` 로 그 필드만 CAS 갱신한다 — 문서 전체를 `writeDocRaw` 로 되쓰면 직원 편집을 덮는다.
- **파트너 경계**: 파트너 토큰은 `/api/partner/*` 에서만 통한다(`crm-api.mjs` 라우터 맨 앞에서 `handlePartnerApi` 로 넘김). 포털 응답에 전화·이메일·메모·내부 단계를 싣지 않는다(`inboundView`·`outboundView`). 파트너 표는 `crm_partner_*`, 문서는 `partners`·`referrals` — 나중에 워커를 떼어낼 단위.
- **응답 계약**: `/api/docs` → `{docs, now}` · `/api/hubspot/queue` → `{items, counts}` · `/api/hubspot/status` → `{connected, reason, portal, queue, pull, map, automation}` · `/api/hubspot/sync` → `{ok, automation}` (`enabled,intervalMinutes,lastRunAt,lastSuccessAt,lastResult,error,running`) · `/api/hubspot/pull` → `{created, updated, conflicts, invalid, deleted, seen, total, more, retry, cursor}` · `/api/partner/referrals` → `{inbound, outbound}`. 바꾸면 app.js·partner.js 를 같이 맞춘다.
- **빌드 스탬프**: `index.html`·`partner/index.html` 의 `./…?v=dev`·`../…?v=dev` 만 해시로 바뀐다. 새 정적 파일을 더하면 `?v=dev` 로 참조하고 `build.mjs` 의 복사 목록(app/·partner/·crm-core.js)에 들어가는지 본다. `dev-server.mjs` 의 `APP_FILES` 도.
- **마이그레이션**은 전부 `IF NOT EXISTS`, 새 파일은 `003_….sql` 부터. 배포 워크플로우가 매번 전부 다시 적용한다. 컬렉션 허용 목록은 표가 아니라 `crm-api.mjs` `COLLECTIONS`(= `CORE.COLLECTIONS` − staff).
- **시크릿**: HubSpot 토큰은 `HUBSPOT_ACCESS_TOKEN` 워커 시크릿뿐. 응답·로그·문서·테스트에 토큰을 넣지 않는다(테스트는 `env.HUBSPOT_FETCH` 가짜 fetch + `pat-test`).
- **시간**: 서버는 UTC 로 돌지만 기본 날짜는 `kstToday()`(한국 시간). 화면은 기기 시간. 날짜는 전부 `YYYY-MM-DD` 문자열.

## 4. 가장 잦은 작업

- **HubSpot 단계·속성이 바뀌었다** → 허브스팟 탭 [HubSpot 파이프라인 불러오기] → 매핑 손보기 → [매핑 저장]. 코드 수정 없음.
- **팔로업 간격·조직 이름** → 관리 탭 설정. `settings.followupOffsets`.
- **큐가 보류·실패로 쌓인다** → `UNMAPPED`(매핑 저장) · `LINKED`(같은 연락처가 다른 리드에 연결됨 — 원본 대조 후 수정)를 확인한다. 429·401은 승인 상태에 남아 다음 주기에 다시 확인한다. `HUBSPOT_AUTH`는 먼저 권한·키 등록 상태를 확인하고, 실제 교체가 필요할 때만 시크릿 등록·배포 절차를 따른다. 다른 일반 실패는 [다시 시도]를 쓸 수 있지만 `UNCERTAIN`은 아래 규칙을 따른다.
- **자동 동기화가 보류된다** → `REMOTE_BASELINE`은 기존 큐 검토 후 첫 가져오기, `REMOTE_CONFLICT`는 양쪽 원본 비교. `UNCERTAIN`은 재시도하지 않고 실제 외부 반영 여부부터 확인한다. 실패 [이 전송 취소]는 반려 후 가져오기가 HubSpot 값을 적용할 수 있음을 확인한 뒤 실행한다. `SEARCH_LIMIT`은 변경분 검색의 10,000건 시간창 제한이다. 자동 분할은 없으며 원본 대조 후 [전체 가져오기]의 기본 목록 보정을 시작할 수 있다.
- **문의 원문에 전화번호가 섞여 저장이 막힌다** → 전화 칸에만 적는 규칙이다(의도). 메모·기록도 같다.

- `app-sync.test.cjs` — 실제 앱의 원장 자동화 제어·서버 응답 확인·busy/세션 종료·오류/부분 결과, 최초 편집 버전·수정 중 원격 변경·초안 보존·항목 재적용·삭제 보호, UNCERTAIN 재시도 차단·실패 취소 확인.

- `crm-core.test.cjs` — 단계·채널/HOT 감지·재검사·팔로업·초안·검증·크레딧·자동 매핑·오늘 보드·KPI·검색·병합·라우트·파트너·PII.
- `hubspot.test.mjs` — 가짜 fetch 로 요청 모양(검색 시간창·기본 목록 커서·속성 생성/PATCH·딜·노트·배치 읽기)·변경 필드 변환(리드↔연락처·딜 적용)·통신 실패.
- `app-modal.test.cjs`·`app-relationships.test.cjs` — 모달 입력·키보드 초점·관계 기록 저장/재조회·불확정 결과/충돌 복구·HubSpot ID와 본문 PII 구분.
- `crm-api.test.mjs` — node:sqlite 대역 + 가짜 HubSpot: 인증·문서 규칙·큐·push·pull·파트너 포털·내보내기, 자동화 권한/매핑/기존 대기 보존·전역/고객 선점·CAS·원격 비교 기준·실패/미확정 보호·딜 순환 조회·검색 커서/한도·전체 커서 이어가기·24시간 보정. 시간 의존 로직이 있으므로 변경 뒤 경합 관련 검사를 확인한다.
