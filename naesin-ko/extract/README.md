# 출판사별 PDF → 팩 업데이트 절차

시험기마다 반복되는 작업이다. **자동화의 목표는 "사람이 없어도 되는 것"이 아니라
"사람이 검수만 하면 되는 것"이다.** 아래 5단계 중 [1][2][4]는 기계가, [3][5]는 사람이 한다.

> 저장소는 public이다(CLAUDE.md 절대 규칙 1). **PDF도, 추출 결과도, 팩 JSON도 커밋하지 않는다.**
> 여기 있는 것은 도구뿐이고 자료는 작업 폴더(예: `~/wb-packs/`)에만 산다. 저장소에 들어가는
> 유일한 콘텐츠는 자체 창작 픽스처(`naesin-ko/pack-sample.json`, 이 폴더의 테스트 fixture)다.

---

## 0. 한 번만 하는 준비

```bash
pip install pymupdf     # 색 정보를 주는 유일한 추출기. 앱·CI와 무관한 오프라인 도구다.
```

작업 폴더 구조 — 시험기·출판사·단원으로 나눈다. 팩 id 규칙과 같은 순서다.

```
~/wb-packs/2026-2/cheonjae-nomisuk-m2-2-U1/
  pdf/     이해완성-저녁항구.pdf  요약노트.pdf  단원집중.pdf  서술형공략.pdf
  spans/   (1단계 산출물)
  works/   (2단계 산출물 — 검수 대상)
  pack.json (4단계 산출물 — 업로드용)
```

## 1. 자료 점검 — 새 출판사면 여기서 5분 쓴다

같은 족보닷컴 상품이라도 출판사·연도가 바뀌면 **색 팔레트가 다를 수 있다.**
빈칸 정답이 `#ffffff`가 아니라 `#e5e5e5`나 다른 연회색인 자료가 있다.

```bash
python3 naesin-ko/extract/pdf-spans.py pdf/이해완성-저녁항구.pdf --colors
```

```
#000000   4120  일을 마치고 돌아온
#ffffff    118  자유
#2b5686     93  헤아린다: 하나씩
```

- 두 번째로 많은 색이 "안 보이는 색"이고 예시 글자가 **정답처럼 보이면** 그대로 진행한다.
- 처음 보는 연회색이 있으면 `build-ihae.mjs`의 `PALE` 배열에 추가하고 테스트를 돌린다.
- 날개풀이 색이 다르면 `NOTE_COLORS`에 추가한다. 안 해도 되지만 하면 날개풀이가 시행에
  섞이지 않는다.

**쪽 수가 홀수이거나 선생님용이 없으면** 짝 대조가 꺼지고 "색만으로 판정" 모드가 된다.
그때는 색 박스 안의 흰 라벨('핵심', '1연' 같은 것)이 빈칸으로 잘못 잡힌다 —
초안 보고서 첫 줄에 `대조본 없음`이 찍히므로 검수에서 그 줄들을 지운다.
가능하면 **학생용+선생님용이 한 파일에 든 원본**을 받는다. 이게 이 파이프라인의 전제다.

## 2. 추출 — 보통은 한 줄이다

폴더를 통째로 넘긴다. 시리즈 판별·추출·메타 교차 보강·작품 병합·id 부여를 다 한다.

```bash
node naesin-ko/extract/build-pack.mjs "~/WB 학습자료/naesin-ko/2026-2/2022-cheonjae-nomisuk-m2-1-U1"
```

```
[단원 팩 초안]
  팩 id 2022-cheonjae-nomisuk-m2-1-U1
  자료 5개: 단원집중 · 서술형 공략 · 직전 요약노트 · 이해완성 · 이해완성
  작품 4 · 지문 세트 14 · 저장 문항 27
  개념 단위(빈칸) 175 · 어휘 14 (같은 개념 153개를 합쳐 328 → 175. 나머지 문맥은 회전 변이로 남김)
  메타: 천재(노미숙) · 중2 · 1학기 · 1. 문학을 펼치면 · 2022 개정
  검수 대기 40건 — 루브릭 미저작 서술형·대조 미달 등. 팩에 넣지 않았습니다.
```

`_build/pack/` 과 `_build/review/` 가 나온다. **둘은 절대 안 섞인다** — 검증기와 관리 웹은
팩 루트와 `works/` 한 겹만 읽으므로 검수 부속물이 학생 기기까지 갈 길이 없다.

시리즈 하나만 따로 돌리고 싶으면(디버깅·부분 재추출) 낱개 도구를 쓴다:

```bash
python3 naesin-ko/extract/pdf-spans.py pdf/이해완성-저녁항구.pdf > spans/ihae-1.json
node naesin-ko/extract/build-ihae.mjs spans/ihae-1.json \
     --workId w-1-1-1 --title "저녁 항구" --review review/w-1-1-1.json > works/w-1-1-1.json
```

낱개 도구는 서로 모르므로 **id 충돌과 조각 병합을 사람이 책임진다.** 평소에는 `build-pack.mjs` 를 쓴다.

2단계는 stderr로 **초안 품질 보고**를 낸다. 이 숫자를 눈으로 대조하는 것이 검수의 시작이다.

```
[이해완성 초안]
  페이지 14 (학생용 7쪽 사용 · 선생님용과 대조해 빈칸 판정)
  개관: 갈래 2 · 성격 3 · 특징 4 · 주제 있음
  본문 5연 12행 · 날개풀이 9 · 연 요지 5
  빈칸(개념 단위) 112
  검수 후보(구절+해설) 47

[검수에서 할 일]
  · author(작가) — 이해완성에는 인쇄돼 있지 않다
  · keywords·rhetoric·speaker는 자동 배정하지 않았다 — candidates 를 보고 검수에서 채운다
  · marks(㉠ 기호)는 문제집 쪽 자료에서 나온다 — 여기서는 비어 있다
```

**연 수·행 수가 지면과 다르면 거기서 멈춘다.** 뒤 단계를 아무리 잘해도 정본이 틀리면
학생이 틀린 것을 외운다.

### 무엇이 자동이고 무엇이 사람 몫인가

| 항목 | 자동 | 왜 |
|------|------|-----|
| 개관(갈래·제재·성격·주제·특징) | ✅ | 표 라벨이 고정이다 |
| 본문 연·행 | ✅ | x 기둥 + 행 간격으로 갈린다 |
| 날개풀이 + 걸리는 시행 | ✅ | 색이 다르고 바로 앞 행에 걸린다 |
| 연 요지(composition) | ✅ | 오른쪽 기둥의 `N연 …` 패턴 |
| **빈칸 + 정답**(가장 큰 덩어리) | ✅ | 학생용/선생님용 색 대조 — 아래 참조 |
| 작가명 | ❌ | 이해완성에 인쇄돼 있지 않다. 업로드 폼에서 넣는다 |
| keywords·rhetoric·speaker | ❌ | 전략 절 표 구조가 작품마다 달라 오배정이 위험하다. `candidates`로만 모은다 |
| marks(㉠ 앵커) | ❌ | 문제집(단원집중) 쪽 자료에서 나온다 |
| 구조도(마인드맵) | ❌ | 다이어그램이라 사람이 옮긴다 |

**빈칸을 어떻게 아는가 — 이 파이프라인의 핵심이자 기획서 §7 추정을 뒤집은 발견:**
이해완성은 같은 지면을 앞은 학생용, 뒤는 선생님용으로 두 번 싣는데 **텍스트 레이어가 같고
학생용은 정답 글자의 색만 흰색으로 바꿔 둔다.** 지면을 이미지로 대조할 필요가 없다.
두 쪽의 같은 좌표를 비교해 "학생용에선 안 보이는데 선생님용에선 보이는 글자"가 정답이다.
흰 글씨라고 다 정답은 아니다(박스 라벨도 흰색) — 그건 선생님용에서도 흰색이라 저절로 걸러진다.
기획서 §7 난점 표는 "빈칸 음영 대조 = 최대 검수 비용"으로 잡았으나, 실측 결과 **거의 전량 자동**이다.

## 3. 검수 — 사람이 하는 단계 (건너뛰지 않는다)

`works/*.json`을 열고 순서대로 본다. **글자 단위로 본다** — 모범답안의 글자 하나가 틀리면
채점기가 오판한다(기획서 §7).

1. `_report`의 연 수·행 수를 지면과 대조
2. `overview` 다섯 항목 — 빈칸이 채워진 값인지(`□`가 남아 있으면 대조 실패)
3. `blanks[]` 훑기 — 정답이 한 개념 단위인지, 문맥(`text`)만으로 답이 유일한지
4. `title`·`author`·`unitPath` 채우기
5. `candidates[]`를 보고 `keywords`·`rhetoric`·`speaker` 배정
6. 원본 오탈자는 **고치지 않고** `notes`에 적는다(`naesin/pack-schema.md` 원칙 3)

실측: 시 1편 기준 자동 추출 **약 3초**, 검수 대상은 빈칸 114개 + 후보 47개다.
기획서 §7이 잡은 "자료 1종당 1.5~3시간"은 이 도구가 생기기 전 추정이다 —
Phase 0에서 스톱워치로 재서 그 값으로 총량을 다시 산출한다(§7 대응 ①).

---

## 4. 조립·검증

작품 JSON들을 팩 하나로 묶고 스키마를 건다. 검증기는 관리 웹과 **같은 순수 모듈**
(`naesin-ko/pack-check.js`)이라 CLI에서 통과한 팩은 업로드 화면에서도 통과한다.

```bash
node naesin-ko/pack-validate.mjs ~/wb-packs/2026-2/cheonjae-nomisuk-m2-2-U1/
```

`errors`가 하나라도 있으면 업로드하지 않는다. `warns`는 읽고 판단한다.

## 5. 배포

관리 웹 `/admin/naesin-ko-admin.html` → **팩 업로드**에 `pack.json`을 넣는다.
브라우저가 같은 검증기를 한 번 더 돌리고, 통과하면 서버(KV)에 저장된다.
그다음 **시험 등록**에서 이 팩 id를 시험 범위에 넣어야 학생 화면에 뜬다.

`_build/review/review.json` 도 같이 골라도 된다. 업로드 화면이 그것만 따로 빼서
**팩이 아니라** 루브릭 저작 대기 목록(`/admin/pending`)으로 보낸다 — 파일 선택기가 폴더를
통째로 복사하기 때문에, 안 빼면 초안이 학생 기기까지 간다(§7[3]).

### 루브릭 저작 — `review.pending` 이 팩으로 들어가는 유일한 통로

같은 화면의 **서술형 루브릭 저작** 카드에서 한다. 왼쪽이 자료(발문·조건·모범답안·해설),
오른쪽이 저작 칸(요소 이름·인정 키워드·배점)이고 모범답안의 어절을 누르면 키워드로 들어간다.

저장 전에 **모범답안으로 검산**한다 — 학생 앱과 같은 `grade.js` 의 `gradeRubric` 을 그대로 부른다.
보는 것은 verdict 가 아니라 **요소가 다 충족되는가**다: 자료의 모범답안이 어절 나열이라 조건·문장
완결에서 걸리는 문항(실측 1건)은 루브릭 잘못이 아니므로 `넣어도 됨` 으로 지나가고, 요소를 못 채우는
루브릭만 막는다. 모범답안이 아예 없는 문항은 `검산 못 함` 으로 표시된다 — 넣을 수는 있지만 표본
채점이 필요하다. 통과한 문항만 `items` 로 옮겨 팩을 다시 검증하고(`counts` 는 조립기가 다시 센다),
**`POST /admin/rubric` 한 요청**으로 팩 추가와 대기 제거를 함께 맡긴다(둘을 나눠 부르면 어긋난다 —
`naesin-ko/README.md` 서버 API 절).

CLI 로 저작하고 싶으면 `review.json` 의 `pending[]` 항목에 `rubric` 을 채워 `items` 로 옮긴 뒤
`pack-validate.mjs` 를 돌려도 결과는 같다 — 검산만 사람 몫으로 남는다.

이해완성만 먼저 올려도 사다리 1~4단계가 돈다. 문제집 자료는 증분으로 올린다.

## 나머지 시리즈 3종 — 현재 상태

| 시리즈 | 뽑을 것 | 도구 |
|--------|---------|------|
| 이해완성 | Work 정본(개관·연/행·날개풀이·연 요지) · blanks | `build-ihae.mjs` |
| 직전 요약노트 | 요약 빈칸 · vocab · checklist · examPoints(★) · 개관 대조 | `build-yoyak.mjs` |
| 단원집중 | PassageSet · 객관식 Item(선지별 해설·부정발문·&lt;보기&gt;) · 작가 · ㉠ | `build-danwon.mjs` |
| 서술형 공략 | 서술형 Item(조건·모범답안·채점 요소) · 발췌 지문 · 작가 | `build-seosul.mjs` |

넷 다 `build-pack.mjs` 가 알아서 부른다. 시리즈 판별은 **파일명이 아니라 지면 내용**이다.

실측 1단원(천재 노미숙 중2-1, 자료 5개 59쪽) 결과: 작품 4(정본 2 + 지문 전용 2) ·
빈칸 175(병합 전 328) · 어휘 14 · 지문 세트 14 · 문항 27 + 검수 대기 32. PDF에서 여기까지 1.5초.

### 같은 개념을 가리키는 빈칸은 합친다

자료는 같은 핵심어를 여러 자리에서 뚫는다. 이해완성과 요약노트가 같은 표의 같은 칸을 각각
뚫고, 이해 전략 절이 본문의 같은 개념을 또 뚫는다. 그대로 두면 **학습량이 개념 수가 아니라
지면 수에 비례한다** — 실측 1단원에서 빈칸 328개, 안정화까지 하루 66개였다.

병합기가 두 갈래로 합친다:

| 갈래 | 규칙 | 왜 |
|---|---|---|
| ① 같은 자리 | 같은 `path` + 같은 정답 | 두 자료가 같은 칸을 뚫은 것. 의심의 여지가 없다 |
| ② 같은 개념 | 같은 정답(자리는 달라도), **두 글자 이상** | 같은 개념을 다른 문장에서 뚫은 것. 한 글자('원'·'배'·'집')는 같은 글자라고 같은 개념이 아니라 ①에서만 합친다 |

**문맥은 버리지 않는다.** 나머지 문맥은 `alts` 로 남아 회전마다 다른 문장으로 나온다 —
같은 문장을 네 번 채우면 문장을 외우고, 다른 문장에서 꺼내야 개념을 외운다(인출 변이).
대표 문맥은 정본에 가까운 것부터 고른다(개관·본문 > 구성·날개풀이 > 전략·출제 Point).

실측 1단원: **328 → 175**(153개 합침), 안정화 하루 66개 → **36개**. 검증기 경고도 66 → 12건.

### 지문 세트를 살려 문항을 되찾는다

추출기는 자기 파일만 본다. "이 지문이 어느 작품인가"를 못 정하면 세트를 검수로 내리는데,
그러면 **그 세트를 가리키던 문항도 함께 빠진다** — 실측 1단원에서 27문항 중 16개가 그랬다.
폴더 전체를 보는 병합기에는 답이 있는 경우가 많아 세 가지를 해결한다:

| 상황 | 처리 |
|---|---|
| 제목은 있는데 그 작품의 이해완성이 폴더에 없다 (시조·소설 발췌) | **정본 없는 작품**(`hasCanon:false`)으로 세우고 지문은 발췌로 담는다. '개념 단위가 없다'는 뜻이고 실제로 그렇다 |
| 제목이 아예 인쇄돼 있지 않은 발췌 | 그 자료의 **제목 있는 발췌 작품이 정확히 하나뿐일 때만** 그것으로 본다(인쇄물이 제목을 맨 앞에 한 번만 찍기 때문). 후보가 둘 이상이면 추론하지 않는다. 추론한 것은 `review.inferred` 에 남는다 |
| 본문도 제목도 없다 | 그대로 검수로. 지문 없는 문항을 팩에 내지 않는다 |

정본 없는 작품을 참조하는 지문은 반드시 `kind:'excerpt'` + 본문이다. `full` 은 '작품 정본에서
가져다 쓴다'는 뜻이라 정본이 없으면 화면이 텅 비는데, **검증기는 이걸 못 잡는다.**

실측 1단원: 작품 2 → 4(지문 전용 2), 지문 세트 6 → 14, 저장 문항 11 → **27**, 지문 없는 문항 0.

### 자동화하지 않은 것과 그 이유

| 안 뽑는 것 | 왜 |
|---|---|
| 서술형 루브릭 | 채점 핵심어가 25문항 중 8개 안팎에만 인쇄돼 있다. **빈 rubric 은 배포 차단 오류**라, 저작한 뒤 `review.pending` 에서 `items` 로 옮기는 순서를 도구가 강제한다(관리 웹 '서술형 루브릭 저작' — 5장) |
| `targetRefs`(문항→개념 단위) | 자료에 대응 정보가 없다. 문자열로 억지 매칭하면 오답이 엉뚱한 빈칸 큐로 돌아가 학생이 상관없는 것을 외운다 |
| keywords·rhetoric·speaker | 표 구조가 작품마다 달라 오배정 위험이 크다. `review.candidates` 로만 모은다 |
| 작가·제목 확정 | 후보는 뽑지만 &lt;보기&gt; 안 인용 출처가 같은 자리에 와서 함께 걸린다 |
| 구조도 | 다이어그램이라 텍스트 레이어에 없다 |
| 개정 연도 | 자료 어디에도 인쇄돼 있지 않다 — `_meta.txt` 에 적는다 |

## 알려진 한계 — 다음 자료에서 먼저 깨질 자리

표본이 **한 단원(천재 노미숙 중2-1, 시 2편 + 산문 1편)** 뿐이다. 적대적 검증에서 나온
'조용히 틀릴 수 있는' 자리를 적어 둔다 — 새 출판사·새 갈래 자료를 처음 돌릴 때 여기부터 본다.

- **본문 글꼴 크기를 값으로 거른다.** 0.1pt만 달라도 발문·조건이 빈다. 발문이 빈 문항은
  검증기가 막지만(`stem 없음`), 추출기의 개수 검산은 마커만 세므로 '일치'라고 초록불을 켠다.
  → 산출물의 문항 수가 맞는데 내용이 비면 이것을 의심한다.
- **지문 세트의 시작을 `※ 다음 글을 읽고` 로 잡는다.** '다음 시를 읽고' 같은 표기가 오면
  세트를 못 찾고, 지문 한 통이 앞 문항의 &lt;보기&gt;로 들어갈 수 있다.
- **한 문항에 &lt;보기&gt; 상자가 둘이면 앞의 것이 버려진다.** 두 작품 비교형에서 나올 수 있다.
- **작가 판정이 이름 폭에 기댄다.** 다섯 자를 넘는 이름(번역 소설·공동 저자)에서 제목·작가가
  본문 첫 줄로 섞일 수 있다.
- **단(column)을 가로지르는 넓은 상자**는 기둥 경계에서 반으로 잘린다.
- **한 폴더에 같은 시리즈의 다른 회차를 넣으면** 문항 id 가 겹칠 수 있다 — 회차별로 폴더를 나눈다.

공통 대응: 새 자료를 처음 돌리면 **개수(문항·세트·빈칸)와 표본 5건을 지면과 눈으로 대조**한다.
어긋나면 그때 도구를 고친다 — 추측으로 미리 넓히지 않는다.
