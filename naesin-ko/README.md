# 국어브레인 — 국어 내신 시험대비 앱

족보닷컴 구매 자료(또는 강사 자체 제작 정본)를 구조화해 재원생에게 원내 전용으로 제공하는 학습 앱.
내신브레인(영어)의 **형제 앱**이고 같은 서버·같은 학생 토큰을 쓴다.
정본 기획서: `docs/국어내신-학습웹앱-기획서-v1.md` (v1.1).

**최종 도달 목표 3가지** — 모든 설계가 여기로 정렬된다:
① 구절→개념 적용(지문을 보고 표현법·시어 의미·화자 태도를 근거와 함께 판별)
② 서술형 조건 충족 답안 ③ 작품 정본 정착(주석 복원·안정화).

> 영어의 "백지 영작"에 해당하는 목표는 국어에 없다. 국어 지필 문항은 예외 없이 **지문을 제시하고**
> 적용을 묻기 때문에, 훈련도 지문이 있는 상태로 한다(반응 일치성, 기획서 §1.4-7).

핵심 데이터 흐름: **자료 → [추출·검증] → 팩 JSON → 관리 웹 업로드 → KV(`naesinko:pack:<id>`)
→ 학생 앱이 인증 후 로드**. 팩은 저장소·정적 자산에 절대 없다.
`concepts.json`만 예외 — 자체 창작이라 커밋하고 정적으로 서빙한다(`concepts.test.cjs`가 그 전제를 지킨다).

## 학생 앱 동작 요약

- **사다리 5단계**: 읽기(본문·날개풀이·구조도·TTS) → 개념 빈칸(SRS) → 구절 적용(생성 문항)
  → 주석 복원(힌트 없이 쓰기) → 서술형.
  **3·4단계 화면에서는 날개풀이가 보이지 않는다** — 그게 곧 정답이라 인출이 성립하지 않는다.
- **작품 완료** = 적용 정답률 기준(기본 80%) + 주석 복원 통과 + 서술형 통과. 4단계 하나로 선언하지 않는다.
- **게이트**는 어휘가 아니라 **적용 정답률**이다. 어휘·개념어는 시험기간 관문이 아니라 상시 큐다
  (국어 어휘·문법은 벼락치기가 안 된다는 통설, 기획서 §1.4-6).
- **D-21 플랜**: intake(D-21~15) → apply(D-14~8, 서술형 착수) → restore(D-7~4) → mock(D-3~2) → taper(D-1).
  서술형 배점이 30% 이상인 시험은 서술형을 D-21부터 낸다.
- **서술형 3층 채점**: 루브릭 규칙(1층 — 조건·요소·문장 완결) → AI 닫힌 판정(2층, Phase 2) → 강사 확정(3층).
  핵심어만 나열한 답안은 통과하지 않는다.
- **학교 오버레이**: 정본의 정답을 학교 선생님 해석으로 덮어쓴다. 채점기·생성기가 그 값을 따른다.
- 상태는 localStorage(`wbk.v1`) 정본 + 서버 백업. **요약·서술형 답안·오버레이는 state와 분리**된
  별도 키에 저장한다 — 관리 overview가 state를 통째로 읽지 않게(기획서 §8 저장 예산).

## 서버 API (naesin-ko-api.mjs)

학생(토큰): `GET /pack?id=` → `{pack, updatedAt}` · `GET/PUT /state`(`{state, summary}`, 256KB)
· `GET /exam` → `{exam, scope}` · `GET /task` → `{task, scope}` · `GET /overlay` → `{overlay, scope}`
· `GET/POST /review` → `{reviews, updatedAt}`

관리(PIN): `POST /admin/pack {id, pack}` (4MB, packId 일치 검증) · `GET /admin/packs`
· `POST /admin/exam {scope, examDate, packIds, profile}` · `GET/POST /admin/task`
· `GET/POST /admin/overlay` · `GET/POST /admin/review` · `GET /admin/overview`

## 팩 제작 파이프라인

1. **원천**: 족보닷컴 시리즈 4종 — 이해완성(작품 정본·빈칸), 직전 요약노트(체크리스트·어휘·빈칸판),
   단원집중(객관식 21 + 서술형 2, 선지별 해설), 서술형 공략(서술형 25). 출판사가 달라도 틀이 같다.
   **또는** 강사 자체 제작 정본(라이선스 경로에 따라, 기획서 §10-1).
2. **추출**: PDF는 복사 금지 플래그가 있지만 **텍스트 레이어 추출은 된다**(색까지 필요해 PyMuPDF를 쓴다).
   텍스트에 없는 것은 빈칸(흰 상자)·연결선·구조도·★·밑줄 — 도형 정보라 렌더링(비전)으로 보정한다.
   추출은 오프라인 Node 스크립트로 하고 관리 웹은 JSON 업로드·검증만 맡는다.
3. **알려진 난점**: 같은 작품의 세트별 기호 위치 차이 · 2단 조판 읽기 순서 ·
   **개정·출판사·작가·학기 미표기**(자료마다 다름) ·
   **서술형 루브릭은 27문항 중 20문항을 사람이 저작해야 한다**(이제 검수 비용의 최대 항목).
   빈칸 복원은 더 이상 난점이 아니다 — 아래 참조.
4. **검증**: `node naesin-ko/pack-validate.mjs <팩 디렉터리>` — 오류 0이어야 배포.
5. **업로드**: `/admin/naesin-ko-admin.html` → 파일 전부 선택(브라우저가 병합·재검증) → 업로드 → 시험 등록.

**자료 폴더 규칙은 `docs/자료-폴더-표준.md`, 추출 절차는 `naesin-ko/extract/README.md`가 정본이다.** 요약:

```bash
pip install pymupdf                                        # 한 번만
node naesin-ko/extract/build-pack.mjs "<단원 폴더>"          # 폴더 하나 → 팩 초안 + 검수 부속물
node naesin-ko/pack-validate.mjs "<단원 폴더>/_build/pack"   # 오류 0 → 관리 웹 업로드
```

폴더 이름이 곧 팩 id이고, 시리즈는 **파일명이 아니라 지면 내용**으로 판별한다(드라이브에서 한글
파일명이 깨진다). 4종 추출기를 `build-pack.mjs` 가 묶어 부르고, 못 뽑은 것은 팩이 아니라
`review/` 로 내린다 — 지문 없는 문항, 루브릭 없는 서술형, 좌우 대조 미달이 그 자리다.

**같은 개념을 가리키는 빈칸은 합친다**(§2.2-2). 자료가 같은 핵심어를 여러 자리에서 뚫기 때문에
그대로 두면 학습량이 개념 수가 아니라 지면 수에 비례한다 — 실측 1단원 328개, 안정화 하루 66개.
합치되 문맥은 버리지 않고 `alts` 로 남겨 **회전마다 다른 문장**으로 묻는다(인출 변이).
결과 175개·하루 36개. 규칙은 `extract/README.md` 를 본다.

**빈칸을 어떻게 아는가 — 기획서 §7의 추정을 뒤집은 발견**: 이해완성은 같은 지면을 앞은 학생용,
뒤는 선생님용으로 두 번 싣는데 **텍스트 레이어가 같고 학생용은 정답 글자의 색만 흰색으로 바꿔 둔다.**
지면을 이미지로 대조할 필요가 없다 — 두 쪽의 같은 좌표를 비교해 "학생용에선 안 보이는데
선생님용에선 보이는 글자"가 정답이다. 실측 1편(시 12행) 빈칸 112개가 약 3초에 나왔다.
흰 글씨라고 다 정답은 아니고(박스 라벨도 흰색) 그건 선생님용에서도 흰색이라 저절로 걸러진다 —
이 두 성질을 `build-ihae.test.mjs`가 자체 창작 fixture로 붙들고 있다.

## 현재 상태 (Phase 1a 완료)

**완료**: 기획서 v1.1 · 순수 로직 5모듈 + 추출 도구 6종 + 테스트 11종(200개 이상 검증) · 학생 앱(사다리 5단계·세션·오답노트·
실수 유형·성취도·**준비도**) · 서버 API(저장 예산 분리) · 관리 웹(팩 업로드·시험·과제·오버레이·
서술형 검토·**반 준비도 분포와 위험 학생**) · 공용 개념어 사전 55개 · 자체 창작 체험 팩 ·
**PDF 추출 파이프라인**(`extract/`) · CI·백업·`_headers`·dist 조립 등록.

**준비도(`readiness.js`)** — 기획서 §11 North Star를 학생 한 명의 0~100 한 숫자로 만든다.
축은 사다리 5단계 + 어휘이고 **가중치는 학교 평가계획의 배점에서 온다**(서술형 40%인 학교는
준비도에서도 서술형이 40%). 숫자만 보이면 행동이 안 바뀌므로 늘 '가장 비어 있는 축'을 같이 내고,
그 축은 **사다리에서 열려 있는 것 중에서** 고른다 — 읽기를 안 한 학생에게 구절 적용을 시킬 수는 없다.
전망은 예측이 아니라 제약이다: 안정화는 서로 다른 날 3회전이라 오늘 처음 만난 빈칸은 최소 4일이
걸리고, `minDays > D-day`면 그건 확정된 미달이라 대응이 다르다(범위 축소·병행 모드).

**Phase 1b 백로그** (기획서 §12):
- 회복 편성 안전판(게이트 오버라이드·병행 모드 UI) · 인쇄(주석 복원 시험지·QR) ·
  종이 ○△× 입력 · 출발선 진단 2분 화면 · 개인정보 동의서 개정 반영
- 파일럿: 목표 시험·반·출판사 확정 후 해당 범위 팩 구조화(§12 학사 캘린더)

**Phase 2 백로그**: 서술형 AI 닫힌 판정+캐시 · 표본 감사 · 수업 세트 집계(저장 계층 결정 선행) ·
촬영 채점 · 회복 triage · 종합 모의 · 21시 푸시 · 추출 스크립트 템플릿 4종 · `novel` 정본 축

**라이선스 상태**: 두 갈래 모두 ✅ 해소(2026-09-03 원장 회신). 트랙 A — 족보닷컴이 "학원 내부에서
무료로 사용하는 것은 상관없다"고 답했다(§10-1). 트랙 B — 원작자 관련 부분도 족보닷컴이 문제 없게
해결했다는 확인을 받았다(§10-2). 팩 배포와 원문 표시의 보류가 풀린다.

남은 것은 법적 판단이 아니라 **기록**이다: 두 확인 모두 구두이므로 회신본을 서면으로 받아 보관하고
범위(재원생 한정·무료·외부 배포 금지·이용권 종료 시 삭제)를 같이 적어 둔다(§13-1·§13-2).
'해결'의 범위가 족보닷컴 자료 수록 작품에 한정되는지도 확인한다 — 학원이 따로 넣는 작품은
포함되지 않는다. 그래서 원문 없이 위치 참조만으로도 성립하는 설계는 **지우지 않고 남겨 둔다.**

**미결(원장)**: 기획서 §13-0(시작 조건 — 담당 강사·검수자·파일럿 반·기기·예산) ·
§13-6(원문을 얼마나 보일지 — 전문 / 이해완성 수록 범위만 / 위치 참조).
